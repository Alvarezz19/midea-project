# schemas 模块扩展描述文件：特点总结

本目录下各模块的 JSON Schema 扩展描述文件采用分层设计，核心目标是：
- 让“检索/理解”更像产品说明书（便于语义匹配与推荐）。
- 让“参数约束”可校验、可自动填参（减少幻觉与非法值）。
- 让“拓扑定义”明确端口与连线形态（便于自动组网）。
- 让“生成模板”可直接落成最终流程节点 JSON（便于自动生成工程）。

> 分层基准样例可参考：schemas/扩展描述文件.jsonc

---

## 1. 四层结构在仓库中的落地形态

### 1) 检索与理解层
通常由以下字段承载：
- `description`：面向自然语言的“功能说明 + 适用场景”。
- `keywords`：用于召回/检索的关键词集合。
- `usage_guides`：使用建议、工程约束、典型接线/配置提示。

**特点**：
- 逻辑/定时/累计类更强调“输入输出行为与边界条件”。
- 变量/IO 类更强调“协议/对象名/默认值/掉电保持等工程约束”。
- 应用类更强调“算法机理与调参方式（如 PID）”。

### 2) 参数约束层
通常由 `parameters_schema` 承载：
- 常见类型：`integer` / `number` / `boolean` / `string`。
- 常见约束：`minimum` / `maximum` / `enum` / `default`。
- 常见“派生参数”：`inputsCount`、`outputCount` 等（用于决定端口数量与 `wires` 形态）。

**一个高频模式：动态输入开关**
- 使用 `xxxFromInput` / `xxxEnable` / `inputD` 等布尔参数控制是否“把参数变成输入端口”。
- 同步维护 `inputsCount`，并在 `ports_definition.inputs[].condition` 中声明端口启用条件。

### 3) 拓扑定义层
通常由 `ports_definition` 承载：
- `inputs[]` / `outputs[]`：端口 `index`、`label/name`、`type`、`description`、`condition`。

**特点**：
- 多数模块通过 `condition` 表达“端口是否激活”，用于自动布线/提示 UI。
- `ports_definition` 下端口 `index` 统一从 0 开始（0-based）。对于动态端口（如 `{n-1}`），也应保证可用的最小端口 index 为 0。

### 4) 生成模板层
通常由 `template_json` 承载（对象或数组两种形式都存在）：
- 必备占位符：`{{__GEN_ID__}}`、`{{__FLOW_ID__}}`、`{{__POS_X__}}`、`{{__POS_Y__}}`、`{{wiresArray}}`。
- `inputs`/`outputs` 与 `ports_definition` 的端口数量保持一致。

**特点**：
- 有的模块将 `template_json` 写成数组（常见于固定结构节点）；有的写成对象（常见于更“组件化”的描述）。
- 定时类常附带 `debugView` 这类运行调试字段。

## 2. 各分类模块特点总结

### A. schemas/accumulation（累计类）
典型模块：计数器、累加器、运行时间。

**核心特征**：
- 强“状态保持/累计”：输出与历史状态相关，通常存在复位输入。
- 端口形态相对稳定：
  - `计数器`/`运行时间`：固定 2 输入（信号 + 复位），输出为计数/时间相关值，并包含上限饱和说明（如 16777215）。
  - `累加器`：支持“复位值来自输入”的动态端口（第 3 输入），并通过 `inputsCount` 驱动拓扑变化。
- 参数约束较少或聚焦“时间间隔 + 上下限”。

**常见工程语义**：
- “上升沿触发计数”、“复位优先/复位清零”、“达到最大值保持”。

### B. schemas/application（应用类）
典型模块：PID 控制器、自适应 PID、含湿量/焓值/露点/湿球等应用算法。

**核心特征**：
- 算法复杂、参数多：大量 `number`/`integer` 参数与默认值。
- 动态端口扩展常见：
  - 以 PID 为代表，通过 `inputsOption` 选择开放哪些“参数输入端口”，并用 `inputsCount` 反映输入总数范围。
- 强“控制工程约束”：输出限幅、死区、正反向作用、禁止/无效时输出模式等。

**对生成/连线的影响**：
- 需要在规划阶段先决定是否开放动态输入（`inputsOption` 等），否则拓扑与 `wires` 形态不一致。

### C. schemas/logic（逻辑类）
典型模块：比较判断、线性变换、触发器（SR/RS）、限值、回差、锁存等。

**核心特征**：
- “纯逻辑/数学变换”为主：输入输出明确、组合性强。
- 动态阈值/动态量程很常见：
  - `比较判断`：`inputAuxEnable` 控制阈值是否走第二输入。
  - `线性变换`：`inputD`/`outputD` 控制输入/输出量程是否走动态端口，并用 `inputsCount` 覆盖 1~5 的输入数量。
- 部分模块是“有状态逻辑”（触发器/锁存/边沿触发等），但参数通常较少。

**常见工程语义**：
- 用 `condition` 写清“何时启用某输入端口”，是逻辑类可自动组网的关键。

### D. schemas/timing（定时类）
典型模块：延时开、延时关、定时脉冲、定时更新。

**核心特征**：
- 时间参数标准化：`timeout` + `timeoutUnits`（seconds/minutes/hours/days）。
- 动态时长输入：`timeoutFromInput` 控制是否开放“时长”输入端口，并用 `inputsCount`（1~2）保持拓扑一致。
- 输出多为布尔（触发/使能/脉冲），强调行为描述（输入触发、保持多久、期间输入变化是否影响输出）。
- 常带 `debugView` 方便查看剩余时间等运行态。

### E. schemas/variable（变量/IO 类）
典型模块：变量(软件输入)、常量、引用、系统时间、物理输入/输出、BACnet/Modbus IO、MQTT 订阅/发布、节点监测等。

**核心特征**：
- 处于“控制逻辑边界”：用于把外部数据/协议对象引入流程，或将流程输出暴露给外部系统。
- 模板字段显著更多：常见 BACnet/Modbus/MQTT 等协议配置字段、默认值、掉电保持、优先级等。
- 端口除了“值输出”外，可能包含工程/协议相关附加输出：例如变量模块的“当前优先级”、MQTT 的“更新计数”。

**需要特别注意的工程约束**：
- MQTT：Topic 不支持通配符、Payload 结构约束、对象名全局唯一等信息通常写在 `usage_guides`。
- 命名一致性：部分文件存在字段拼写差异（例如 MQTT 订阅模板中的 `objctName` 可能是 `objectName` 的拼写变体）；下游生成器/校验器需要兼容或在规范中统一。

### F. schemas/others（其他/杂项）
典型模块：备注（Comment）。

**核心特征**：
- 无输入/输出端口，仅用于说明文档化。
- 参数非常少（如 `info` 一个字符串），但 `usage_guides` 会强调 Markdown/换行约束。

## 3. 跨分类的共性模式（便于维护/新增模块）

- 端口动态化：`xxxFromInput`/`xxxEnable` + `inputsCount` + `ports_definition.condition` + `template_json.inputs/wires` 必须同步。
- 输出/数值边界：累计/计时类往往需要在描述里写清“上限饱和/溢出策略”。
- index 统一规范：工具链可按 0-based 端口 index 处理，并对动态端口表达式（如 `{n-1}`）按生成器规则展开。
- template_json 形态差异：需要兼容“对象/数组”两种写法。

## 4. 建议的文档化写法（检索效果更好）

- `description`：一句话定义 + 一句话典型场景 + 一句话关键限制（如上限、死区、通配符不支持）。
- `keywords`：覆盖用户自然语言（如“延时启动/延时开”、“比较/阈值/门限”）。
- `usage_guides`：尽量写成可执行的配置/连线建议（以及关键反例/坑点）。

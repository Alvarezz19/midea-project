背景：

生产级咨询分支需要可控的领域知识底座，但当前没有工程师补充资料。阶段 A 只能先建立语义边界、知识卡格式和 generated 级别的基础知识，不得伪造 reviewed 知识。

目标：

- 建立 L0 受控语义层，统一实体类型、关系类型、风险标签和术语。
- 建立结构化领域知识卡模板和首批 AHU、机房群控、通用规则知识卡。
- 通过 schema 校验保证知识卡元数据、适用范围、证据等级和风险标签可被后续索引构建稳定消费。
- 明确所有未审阅知识卡为 `review_status: generated`。

代码/契约变化：

- 新增 `knowledge/ontology/` 四个受控词表文件。
- 新增 `knowledge/domain/` 下 AHU、plant_room、common 三类知识卡和模板，共 22 张 generated 知识卡。
- 新增 advisory KB schema 校验模块，解析 front matter、证据等级、适用范围、风险标签和章节结构。
- 新增 schema 定向测试，覆盖合法知识卡、未知风险标签、无效状态、缺失章节和知识库批量加载。

影响：

- 咨询分支有了可被机器校验的领域知识输入层。
- 后续阶段可以在不引入未审阅假设的前提下构建检索索引。
- LLM 使用这些知识时必须区分 generated 与 reviewed，避免把未审阅内容当作工程定论。

阶段 A 只解决领域知识卡输入问题，咨询分支还需要从现有模板、点表、代码和规则中抽取可引用的工程事实。阶段 B 的目标是让后续检索能同时引用“领域知识”和“当前仓库事实”。

目标：

- 构建 advisory 专用索引目录 `indexes/advisory/`。
- 从模板、点表、功能块、配置项、保护链路、控制链路、参数统计和代码事实中抽取结构化证据。
- 生成 manifest，记录索引版本、输入来源和每类索引行数。

### ER-20260509-003 咨询知识库阶段 C 混合检索和上下文融合

状态：已完成

修改人：Codex

关联文件：

- `app/services/advisory_kb/loader.py`
- `app/services/advisory_kb/retrievers.py`
- `app/services/advisory_kb/fusion.py`
- `app/services/advisory_kb/context.py`

- `tests/test_advisory_kb_retrieval.py`

- `文档/演进记录.md`
- `文档/演进记录/2026-05-09.md`

背景：

阶段 B 生成了索引，但咨询分支主流程还没有消费这些索引。阶段 C 需要把检索结果融合成 LLM 可用的上下文，同时保持咨询和改图链路隔离。

目标：

- 新增 advisory KB loader、retriever、fusion 和 context builder。
- 将当前工程事实、仓库索引事实和领域知识卡融合为 `advisory_kb_context`。
- 只在咨询问题需要领域知识时注入上下文，不改变明确采纳建议后的补丁规划链路。
- 在 LLM 输出规则和响应摘要中暴露知识来源、风险标签、query plan 和引用依据。

代码/契约变化：

- 新增索引加载和领域知识卡加载能力。
- 新增多路检索：模板画像、页面角色、点位身份、控制链路、保护链路、参数统计、配置模型、领域知识卡和当前工程证据。
- 新增融合排序：当前工程证据优先，风险标签和功能类型影响排序，generated 知识降权。
- `app/services/advisory.py` 在 `should_search_domain_knowledge` 为真时构建 `advisory_kb_context`，LLM prompt 要求引用该上下文并谨慎使用 generated 知识。
- 响应 summary 和 basis 中新增 advisory KB 单元、来源、风险标签和 query plan。
- 修正阶段 C 验收中发现的问题：设备数量变化优先识别为配置模型；配置模型补充 `device_count_topology` 风险标签；当前工程证据分数提高以确保排在首位。

影响：

- 咨询回答可以同时基于当前工程结构、索引事实和领域知识卡生成建议。
- 高风险保护/联锁/设备数量类问题可以在上下文层提前暴露风险标签。
- 主补丁链路仍由采纳后的 intent 进入 semantic locator、planner、dry-run 和风险确认，不由咨询直接改图。

### ER-20260509-004 全量测试超时经验固化

状态：已完成

修改人：Codex

关联文件：

- `AGENTS.md`
- `文档/演进记录.md`
- `文档/演进记录/2026-05-09.md`

背景：

阶段 A/B/C 验收过程中，全量 `pytest -q` 已从约 9 分钟增长到约 12 分钟。使用默认 120s 或 600s 工具超时会导致测试进程被终止，容易被误判为测试失败。

目标：

- 在仓库级说明中写清全量后端回归的超时设置。
- 避免新对话重复使用过短 timeout。
- 区分工具 timeout 和 pytest 失败。

代码/契约变化：

- `AGENTS.md` 新增“测试超时”章节：全量 `pytest -q` 使用至少 900000ms，定向测试可继续使用 120000ms；无失败输出的 timeout 应先长超时重跑。

影响：

- 新对话执行全量回归时更容易一次跑完。
- 减少因为工具超时引发的误修复。

验证：

```powershell
conda activate midea
git diff --check
```

结果：

```text
文档变更校验通过；本条为文档-only，未重新运行全量 pytest。
```

风险/回滚：

- 文档-only，无运行时风险。
- 如后续全量测试耗时继续增长，应同步提高 `AGENTS.md` 中建议 timeout。

文档同步：

- `AGENTS.md`、`文档/演进记录.md` 和本归档已同步。

后续动作：

- 后续阶段验收继续优先跑定向测试；阶段完成时再使用长 timeout 跑全量。

DoD：

- 新对话能从 `AGENTS.md` 直接看到全量 pytest 的 timeout 设置。
- 演进记录包含此次经验和最新验收基线。

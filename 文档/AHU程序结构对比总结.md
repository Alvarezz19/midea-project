## 1. 分析对象

| 文件 | 页签主标签 | 说明 |
| --- | --- | --- |
| `flows_20251210190941.json` | `IO/通讯(三山经开）` | 第一版基准结构 |

| `flows_20260206160555.json` | `IO/通讯(安宁中医院）` | 页签拆分更细，增加排风机页与直膨除湿模板 |

说明：以下总结重点是“结构特点”和“模块组织方式”，不是逐点位的工艺运行逻辑推导。

## 2. 整体结论

这 3 个 JSON 文件本质上都是同一套 AHU 程序模板在不同项目上的实例化版本，采用的是非常典型的“Node-RED/图形流程序”组织方式：

- 顶层是一个扁平数组，不是多层嵌套树。
- 真正的层次关系不是靠 JSON 嵌套，而是靠 `type` 和 `z` 这两个字段建立。
- `tab` 表示页面页签。
- `subflow` 表示可复用子流程模板。
- 普通节点通过 `z` 挂到某个 `tab` 或某个 `subflow` 下面。
- 子流程实例不是普通 `subflow`，而是 `type = subflow:<子流程ID>` 的节点。
- 每个节点除了逻辑参数外，还保存了 `x`、`y`、`wires`，说明 JSON 同时承担“逻辑定义”和“画布布局定义”两种角色。

从工程结构上看，这 3 份程序都遵循同一个主框架：

- 一个 IO/通讯页负责采集、映射、硬件接线和直膨通讯。
- 一个控制页负责主要控制算法与联锁。
- 一个定时页负责定时使能。
- 一个直膨机状态页负责大批量直膨外机状态/遥测点映射。
- 若项目复杂度更高，会把某些功能从控制页中拆成独立页签，例如排风机页、直膨机故障页。

因此，这 3 个文件不是三套完全不同的 AHU 程序，而是“同一控制平台 + 同一模块库 + 不同项目裁剪方式”的关系。

## 3. JSON 结构层面的共同特点

### 3.1 顶层结构是“扁平清单 + 引用关系”

三个文件都不是把一个 AHU 系统写成一棵深层 JSON 树，而是把所有对象平铺在一个数组中。结构依赖以下规则建立：

- `tab` 对象先定义页面。
- `subflow` 对象定义模块接口，包括 `in`、`out`、`inputs`、`outputs`。
- 普通节点使用 `z` 指向所属页面或所属子流程。
- `wires` 在这三份文件中按节点输入端口保存上游来源节点及其端口，形式通常是 `{id, port}`；其数组长度与 `inputs` 一致，而不是与 `outputs` 一致。

这类组织方式的优点是：

- 适合图形化编辑器直接读写。
- 页面级结构、模块级结构、点位级结构可以共存在同一文件里。
- 便于后续复制模板、替换项目点位、增删页签。

### 3.2 页面层与模块层分离明显

这 3 个文件都存在两个层次：

- 页面层：`tab`
- 模块层：`subflow`

页面层承担“功能分区”，子流程承担“复用封装”。这说明作者不是纯粹把逻辑平铺在一个大页面里，而是已经形成了模块化建模习惯。

### 3.3 强依赖软件点与引用点

三份文件中数量最多的节点类型都不是 PID、比较器或开关，而是：

- `swInput`
- `quote`

三份文件中这两类节点合计占比都在 62% 到 64% 左右，说明程序结构的核心不是“算子很多”，而是“点位很多、引用很多、变量编排很多”。

这反映出 AHU 程序的一个典型结构特征：

- `swInput` 用来沉淀软件点、设定值、中间状态、命令量、故障量。
- `quote` 用来在不同区域复用这些点，而不是每处都重新拉线或重复建点。

也就是说，这套程序更像“点位驱动的控制图”，而不是“少量公式驱动的纯算法图”。

### 3.4 通讯层、算法层、执行层分工清楚

三个文件里都能看到比较稳定的节点分工：

- 通讯/点位层：`swInput`、`hwInput`、`hwOutput`、`modbusOutput`
- 引用层：`quote`
- 算法层：`logic`、`switch`、`compare`、`limit`、`pid`、`multiply`、`subtract`、`delayOn`、`delayOff` 等
- 结构层：`tab`、`subflow`
- 注释层：`comment`

这说明程序并不是一股脑把所有逻辑直接接到输出，而是明显经过“点位抽象 -> 算法运算 -> 执行输出”的组织。

### 3.5 既描述控制逻辑，也描述工程画布布局

所有普通节点都带有：

- `inputs`
- `outputs`
- `x`
- `y`
- `wires`

这意味着文件不仅能表达“控制关系”，还记录了“在编辑器里怎么摆放”。因此它既是控制程序源文件，也是项目图纸式的画布存档。

需要特别注意的是，这三份 JSON 里的 `wires` 不是“从当前节点输出到下游节点”的清单，而是“当前节点各输入端口引用哪些上游节点”的清单。例如子流程实例的 `wires` 数组长度等于该实例的输入数量，用来列出每个输入口接入的 `quote`、`swInput` 或常量节点。

### 3.6 没有 group/config 这类额外结构层

三个文件都没有发现额外的 `group` 或独立配置节点层，说明当前组织方式比较“直给”：

- 页面分区靠 `tab`
- 模块复用靠 `subflow`
- 页面内部再靠节点位置、注释、变量命名来维持可读性

这使得结构比较清晰，但也意味着控制页会比较密。

## 8. 各页签的结构特点

### 8.1 IO/通讯页

三份文件的 IO/通讯页都承担以下职责：

- 现场硬件点接入
- 软件点与通讯点映射
- 直膨相关命令或故障点接口
- 部分线性变换、取位、基础逻辑处理

IO 页的数据对比如下：

| 文件 | `modbusOutput` | `hwInput` | `hwOutput` | 结构观察 |
| --- | ---: | ---: | ---: | --- |
| `flows_20251210190941.json` | 16 | 14 | 6 | 基础型 IO 组织 |
| `flows_20251229175702.json` | 16 | 24 | 6 | 硬件采集点明显增多 |
| `flows_20260206160555.json` | 9 | 15 | 7 | 故障点被拆到独立页，物理输出增加 1 个 |

关键观察：

- 第一、第二份把直膨故障输出也放在 IO/通讯页。
- 第三份把 7 个直膨故障相关 `modbusOutput` 拆到了 `直膨机故障` 页，所以 IO 页内 `modbusOutput` 从 16 降到 9，但三个文件总 `modbusOutput` 都还是 78，说明只是重构页面，不是删掉接口。
- 第三份 IO 页内保留的湿度设定输出名为 `湿度设定`，而第一、第二份对应点名为 `直膨湿度设置`，说明同类接口在项目化过程中存在命名收敛或改名。
- 第二份 `hwInput` 达到 24 个，是三份里最高的，说明该项目现场硬件接入更重。

### 8.2 控制页

控制页是三份文件中最核心、最密集的页签。共同特点如下：

- 大量 `swInput + quote` 组成控制变量网。
- 大量 `logic + switch + compare + limit` 形成联锁骨架。
- 主要控制对象包括送风机、冷水阀、电加热、风阀、模式切换、湿度/温度联动等。
- 子流程实例主要挂在控制页，说明这里是主编排区；前两份全部子流程实例都在控制页，第三份则有 3 个在控制页、2 个在 `排风机` 页。

进一步看三份文件的差异：

1. `flows_20251210190941.json`

- 以基础 AHU 控制结构为主。
- 控制页内可以看到送排风、温湿度、紫外灯、冷水阀、电加热等对象。
- `moisture`、`add`、`subtract` 等湿度相关运算存在，说明带有一定湿度控制逻辑。

2. `flows_20251229175702.json`

- 在保持总体框架不变的基础上，控制页更丰富。
- 增加了 `enthalpy` 节点、较多 `delayOut`、更多 `compare` 与 `delayOn/delayOff`。
- 实例化了 `末端组空新风/回风阀CO2控制`，说明这一版真正接入了 CO2 风阀控制。
- 控制页还出现了 `APP开机`、`APP关机`、`M_AD_MC`、`M_AD_AM` 等项目化接入痕迹，说明外部控制接口更多。

3. `flows_20260206160555.json`

- 控制页仍然是主中枢，但部分排风机逻辑已经拆到独立页签，页内组织更清爽。
- 与第二份一样，控制页也包含 2 个 `enthalpy` 节点和 `制冷焓值定值控制`，因此焓值类控制并非云霞项目独有，而是第二、第三份共同具备的扩展。
- 增加了更多湿度/除湿相关算子，例如 `moisture`、`subtract`、`counter`、`runtime` 的组合更明显。
- 电加热部分偏向“预热”场景。
- 额外新增 `直膨除湿` 模板，说明此版本更强调温湿度复合控制的扩展能力。

### 8.3 定时页

三份文件完全一致，均只有 4 个节点：

- `TIME_EN`
- `TIME_CST`
- 一个普通变量点
- 一个逻辑节点

这说明：

- 定时页是一个极简的总使能模块。
- 该部分已经高度标准化。
- 项目变化不会轻易动到这层。

### 8.4 直膨机状态页

三份文件的 `直膨机状态` 页结构几乎完全一致，全部为 154 个节点，其中：

- `swInput` 88 个
- `modbusOutput` 62 个
- 另有少量 `multiply` 和 `comment`

从点名上看，这一页集中映射了：

- 外机台数、系统匹数、外机模式
- 软件版本、外机地址、外机匹数
- 压缩机频率、交流电流、直流母线电流
- 冷凝温度、蒸发温度、冷凝压力、蒸发压力
- 膨胀阀开度

这说明 `直膨机状态` 页是一个高度标准化的状态映射页，项目差异极小，基本可以视为一套复用模板。

### 8.5 第三份新增页签的意义

1. `排风机`

- 共 30 个节点。
- 以两个 `末端组空送风机标准控制` 子流程实例为核心。
- 说明第三份将排风机控制独立成页，并通过控制页中的 `开排风机` 点与主控制逻辑联动。
- 这种做法更利于维护，也更利于多风机对象并列扩展。

2. `直膨机故障`

- 共 14 个节点。
- 由 7 个 `modbusOutput` 和 7 个 `swInput` 组成。
- 本质上是把直膨故障映射独立成一个故障接口页。
- 这属于结构上的“页面解耦”，有利于后续统一排查和维护故障点。

## 9. 三个文件的结构演化判断

如果把这三份文件看成一条演化链，大致可以这样理解：

### 9.1 第一份：基准版

- 标准 4 页签结构。
- 主功能都在，但模块拆分程度中等。
- 控制页承担了较多综合逻辑。

### 9.2 第二份：在基准版上增强功能接入

- 页签数量不变。
- IO 更重，控制页更密。
- CO2 风阀控制真正实例化。
- 引入焓值类控制和更多项目化接口。

### 9.3 第三份：进一步模块化和页签解耦

- 从 4 页签扩展到 6 页签。
- 将排风机控制和直膨故障映射单独成页。
- 增加直膨除湿模板。
- 电加热模块向“预热”方向调整。
- 结构上更像一个可以继续扩展的工程化版本，而不只是单个项目的直接堆叠。

## 10. 最终总结

综合来看，这 3 个 AHU JSON 文件在结构上有以下最突出的特点：

1. 都采用“扁平数组 + `type`/`z` 引用关系”的图形流程序组织方式。
2. `wires` 按输入端口引用上游节点，不能简单按“当前节点输出连到下游节点”理解。
3. 都遵循“IO/通讯页 + 控制页 + 定时页 + 直膨状态页”的标准骨架。
4. 都通过 `subflow` 构建模块库，且模块库规模大于实际挂载规模，说明存在明显的模板化设计思想。
5. 都高度依赖 `swInput` 与 `quote`，反映出程序是以“点位组织”和“引用复用”为核心，而不是以少量大算法块为核心。
6. `直膨机状态` 页和总 `modbusOutput` 数量高度稳定，说明外部通讯接口和状态映射模板比较成熟。
7. 真正变化最大的区域不是基础模板，而是 `控制` 页和 `IO/通讯` 页，说明项目差异主要体现在接入点位、联锁条件、是否启用某些子流程，以及页面拆分粒度上。
8. 第三份文件体现出更强的模块化意识，已经开始把排风机控制、故障映射、除湿模板从大控制结构中分离出来。

如果只用一句话概括这三份文件的结构关系，可以写成：

> 它们不是三套完全不同的 AHU 程序，而是一套统一 AHU 控制模板在不同项目上的逐步裁剪、扩展和模块化演进结果。

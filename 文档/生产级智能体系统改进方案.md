# 生产级智能体系统改进方案

更新时间：2026-04-28

适用范围：本方案用于指导本项目从当前原型升级为可交付、可审计、可回滚、可持续迭代的生产级智能体系统。后续开发默认遵照本文执行；如果业务目标或技术路线发生变化，应先更新本文，再实施代码改造。

## 1. 目标与结论

本项目的最终目标不是“让大模型直接生成完整工程 JSON”，而是建设一个面向工程师的智能改造系统：

1. 用户先明确项目大类：机房群控程序或 AHU 程序。
2. 系统继续对话澄清设备、控制策略、通讯、IO、保护逻辑和导出要求。
3. 系统从对应模板库中选出最接近需求的完整工程模板，并向用户解释选择理由。
4. 系统基于模板创建独立工程版本，不覆盖原始模板。
5. 用户可以多轮提出局部改造要求，系统只生成结构化补丁意图，由确定性工具执行修改、校验和保存。
6. 每次修改都有版本、diff、校验报告和审计记录。
7. 用户满意后，只允许导出校验通过的最终 JSON。

当前仓库已经完成了“可运行原型”的核心闭环，但距离生产级仍有明显差距。最重要的改造方向是：

1. LangGraph 从“临时状态机”升级为“持久化、可中断、可恢复的工作流编排层”。
2. planner 从正则和规则规划升级为“LLM 结构化规划 + 确定性工具执行 + 强校验”的双层架构。
3. 检索从关键词打分升级为“模板级、页面级、节点级、功能块级”的混合检索。
4. 补丁引擎从少量低风险操作扩展到可控的局部子图复制、动态输入、连线修复和回滚。
5. 校验从基础结构校验升级为 schema、拓扑、IO、通讯、保护逻辑和工程规范的多级校验。
6. 前端从原型工作台升级为工程师可用的对话、模板确认、局部图、diff、校验和导出工作台。
7. 增加数据库、权限、审计、观测、评测、部署和备份等生产化能力。

## 2. 调研依据

本方案结合了当前仓库实读结果和官方资料：

1. LangGraph 官方文档将 LangGraph 定位为用于长运行、有状态智能体的底层编排框架，核心能力包括 durable execution、streaming、human-in-the-loop、memory 和生产部署能力。参考：https://docs.langchain.com/oss/python/langgraph/overview
2. LangGraph persistence 文档说明 checkpointer 会按 thread 保存 graph state，并要求通过 `configurable.thread_id` 保存和恢复状态。参考：https://docs.langchain.com/oss/python/langgraph/persistence
3. LangGraph interrupts 文档说明 interrupt 会暂停执行、保存状态，并通过同一个 `thread_id` 恢复；生产环境应使用持久化 checkpointer。参考：https://docs.langchain.com/oss/python/langgraph/interrupts
4. LangGraph durable execution 文档强调使用 checkpointer 后可以从中断或失败处恢复，并要求工作流设计为 deterministic 和 idempotent。参考：https://docs.langchain.com/oss/python/langgraph/durable-execution
5. LangGraph application structure 和 test 文档建议生产应用具备依赖文件、配置文件、graph 定义、环境变量管理和可测试结构。参考：https://docs.langchain.com/oss/python/langgraph/application-structure 和 https://docs.langchain.com/oss/python/langgraph/test
6. FastAPI 官方部署文档强调生产部署需要关注 HTTPS、启动、重启、多进程、内存和启动前步骤。参考：https://fastapi.tiangolo.com/deployment/concepts/
7. FastAPI HTTPS 文档说明反向代理、TLS termination 和 forwarded headers 的部署注意事项。参考：https://fastapi.tiangolo.com/deployment/https/
8. OpenAI 官方结构化输出文档建议使用 JSON Schema 和 `strict: true` 约束模型输出，提升结构化结果稳定性。参考：https://developers.openai.com/api/docs/guides/structured-outputs
9. OpenAI 官方 function calling 文档说明工具调用适合让模型连接外部系统和应用动作。参考：https://developers.openai.com/api/docs/guides/function-calling
10. OpenAI 官方生产和部署清单文档强调密钥安全、使用监控、成本监控、限流和上线前检查。参考：https://developers.openai.com/api/docs/guides/production-best-practices 和 https://developers.openai.com/api/docs/guides/deployment-checklist

## 4. 当前主要缺口

### 4.1 产品流程缺口

1. 用户点击“机房群控程序/AHU 程序”的产品入口还不够明确，目前是下拉选择和自动判断。
2. 系统没有结构化澄清问题机制，无法稳定收集设备数量、执行器、传感器、通讯方式、保护逻辑、导出约束。
3. 模板确认只是候选列表，没有“匹配项、缺失项、预计改造成本、风险点”说明。
4. 多轮修改没有形成清晰的需求清单、待确认事项、已拒绝变更和已确认高风险操作。
5. 没有 JSON diff、局部流程图、影响范围、版本历史和回滚入口。

### 4.2 LangGraph 使用缺口

1. `invoke_workflow` 需要复用应用启动时的单例编译结果，并接入持久化 checkpointer。
2. 没有 checkpointer，`thread_id` 只是 API 层的字典 key，不能用于 LangGraph 原生恢复。
3. 没有使用 interrupt，用户确认点由状态和前端按钮模拟，无法做到真正暂停和恢复。
4. 工作流节点基本是确定性函数，还没有接入 LLM、结构化输出、工具调用或失败重试。
5. graph state 中保留消息列表，但没有长期压缩、结构化摘要和上下文预算控制。

### 4.3 存储与并发缺口

1. `SESSIONS` 是进程内内存，重启丢失，多 worker 不共享。
2. 工程版本以文件为主，缺少数据库中的项目、版本、补丁、校验、审计索引。
3. `/api/projects/{project_id}/versions` 只能从当前进程会话反查，重启后无法查询。
4. 没有用户、项目权限、租户隔离和路径级访问控制。
5. 没有事务边界，补丁应用、保存、元数据、校验报告和审计记录未形成原子提交。

### 4.4 检索与上下文缺口

1. 当前检索主要是关键词和人工特征打分，没有向量检索、BM25、重排和修改成本评估。
2. 缺少功能块级索引，无法稳定定位“水泵轮值逻辑”“防冻保护逻辑”“旁通阀 PID 回路”等局部子图。
3. 节点索引没有足够的上下游语义、端口语义、schema 关联和工程角色。
4. 模板数量只有 5 个，生产效果高度依赖继续扩充模板和标注。
5. `wires` 方向命名必须统一。当前工程 JSON 的连线方向应定义成统一术语，例如 `input_sources` 或 `upstream_refs`，索引、校验、补丁和文档都使用同一套命名。

### 4.5 planner 与补丁能力缺口

1. 当前 planner 是规则和正则，不能理解复杂需求，例如“新增 CO2 控制并联动新风阀”和“把 2 台水泵改为 3 台轮值”。
2. `add_node_from_schema`、`connect`、`disconnect` 虽然在 patch engine 中实现，但自然语言 planner 尚未自动组合这些多步补丁。
3. 尚未实现 `copy_block`、`enable_dynamic_input`、`replace_constant`、`set_io_point`、`delete_node` 等生产必需操作。
4. 没有 dry-run、diff 预览、风险分级、自动回滚和补丁幂等校验。
5. 对动态端口、子流程、跨 tab 连线、IO/通讯点位的改造能力不足。

### 4.6 校验缺口

1. 还没有全工程 schema 参数校验，无法发现节点字段类型、枚举、范围、必填参数和未知字段问题。
2. 动态端口规则尚未完整校验，例如 `inputsOption`、`inputsCount`、`ports_definition.condition` 与 `wires` 是否一致。
3. 还没有 IO 地址冲突、BACnet/Modbus/MQTT 对象名冲突、通讯点表重复校验。
4. 还没有保护逻辑校验，例如防冻、故障、运行反馈、最小启停延时、手自动状态和关键联锁是否被删除或绕过。
5. 校验报告只有 issues，没有修复建议、影响范围和是否阻塞导出的判定策略。

### 4.7 前端与可用性缺口

1. 当前是原型工作台，缺少工程师高频操作需要的局部图、节点搜索、diff、版本列表、回滚、确认记录。
2. 没有流式状态，用户无法看到“正在澄清需求、正在检索、正在应用补丁、正在校验”的过程。
3. 补丁输入仍偏开发者，生产前应改为结构化预览和确认，手写 JSON 只能保留为高级调试入口。
4. 导出前缺少最终检查面板。

### 4.8 安全、运维、评测缺口

1. 缺少认证、授权、CORS、CSRF 策略、路径访问控制和 API 限流。
2. 缺少依赖锁定文件、部署配置、迁移脚本、日志规范、健康检查细分和备份恢复方案。
3. 缺少 LLM 调用日志、trace、成本、延迟、token、失败率、用户反馈和告警。
4. 缺少基准评测集，无法衡量模板选择、需求澄清、补丁规划和校验修复的质量。

## 5. 生产级目标架构

推荐继续沿用“FastAPI + LangGraph + 确定性 JSON 工具链 + 检索库 + 前端工作台”的方向，但拆清边界：

```text
浏览器工作台
  |
  | HTTP + SSE/WebSocket
  v
FastAPI API 层
  |
  | 调用
  v
应用服务层
  |-- 会话服务
  |-- 项目版本服务
  |-- 模板检索服务
  |-- 知识检索服务
  |-- 补丁执行服务
  |-- 校验服务
  |-- 审计服务
  |
  v
LangGraph 编排层
  |-- 项目类型确认
  |-- 需求澄清
  |-- 模板检索与确认
  |-- 修改规划
  |-- 局部上下文加载
  |-- 结构化补丁生成
  |-- 人工确认 interrupt
  |-- 补丁执行
  |-- 校验与修复
  |-- 导出确认
  |
  +--> LLM Gateway
  +--> PostgreSQL
  +--> 向量库或 pgvector
  +--> 模板/工程文件存储
  +--> 观测与评测系统
```

核心原则：

1. Graph state 只保存轻量引用和结构化摘要，不保存完整工程 JSON。
2. LLM 只能生成结构化意图，不能直接保存最终 JSON。
3. 所有工程 JSON 修改必须由 patch engine 执行。
4. 所有导出必须经过校验服务，并且校验报告中不能有阻塞级错误。
5. 所有高风险操作必须有人工确认记录。
6. 所有版本必须可追踪、可对比、可回滚。

## 6. 数据与状态设计

### 6.1 LangGraph state

建议升级为以下结构：

```python
class AgentState(TypedDict):
    messages: list[dict[str, Any]]
    project_type: Literal["plant_room", "ahu"] | None
    requirement_summary: dict[str, Any]
    open_questions: list[dict[str, Any]]
    confirmed_requirements: list[str]
    rejected_changes: list[str]
    selected_template_id: str | None
    current_project_id: str | None
    current_version_id: str | None
    loaded_context_refs: list[dict[str, str]]
    pending_plan: dict[str, Any] | None
    pending_patch: dict[str, Any] | None
    risk_assessment: dict[str, Any] | None
    validation_report_id: str | None
    next_action: str | None
    status: str
```

不应放入 state 的内容：

1. 完整工程 JSON。
2. 大量节点全文。
3. 大型 diff。
4. 原始向量检索结果全集。
5. API key、用户密码、内部路径白名单等敏感配置。

### 6.2 数据库存储

生产阶段建议使用 PostgreSQL，至少建立以下表：

| 表 | 用途 |
| --- | --- |
| `users` | 用户身份 |
| `projects` | 用户项目 |
| `project_versions` | 不可变工程版本，记录父版本、模板来源、JSON hash、文件路径 |
| `patch_records` | 每次补丁请求、补丁内容、执行结果、风险等级 |
| `validation_reports` | 每次校验报告和阻塞状态 |
| `sessions` | API 会话与当前项目状态 |
| `audit_events` | 用户确认、导出、回滚、失败、权限拒绝等事件 |
| `template_catalog` | 模板元数据 |
| `tab_index` | 页面索引 |
| `node_index` | 节点索引 |
| `block_index` | 功能块索引 |
| `knowledge_chunks` | 知识库分块 |

工程 JSON 文件可以继续存文件系统，生产部署可迁移到对象存储。数据库中保存路径、hash、大小、来源、父版本和校验状态。

### 6.3 版本模型

每次成功修改创建新版本，不直接覆盖当前版本：

```text
template_version
  -> v1_user_project_created
  -> v2_patch_rename_node
  -> v3_patch_add_co2_logic
  -> v4_final_exported
```

版本元数据必须包含：

1. `project_id`
2. `version_id`
3. `parent_version_id`
4. `source_template_id`
5. `json_sha256`
6. `patch_record_id`
7. `validation_report_id`
8. `created_by`
9. `created_at`
10. `exportable`

## 7. LangGraph 改造方案

### 7.1 工作流节点

推荐生产主流程：

```text
START
  -> confirm_project_type
  -> extract_requirement
  -> ask_clarifying_questions
  -> retrieve_template_candidates
  -> explain_template_candidates
  -> interrupt_template_confirmation
  -> create_project_version
  -> plan_change
  -> retrieve_relevant_context
  -> generate_structured_patch
  -> risk_check
  -> interrupt_high_risk_confirmation
  -> dry_run_patch
  -> validate_dry_run
  -> summarize_diff
  -> interrupt_apply_confirmation
  -> commit_patch_version
  -> wait_next_user_action
      | 继续修改 -> extract_requirement
      | 导出 -> final_validate -> export_json -> END
```

### 7.2 必须改造项

1. Graph 在应用启动时构建和编译一次，通过依赖注入传入 API 层。
2. 使用持久化 checkpointer，生产优先 PostgreSQL checkpointer；测试可用内存 checkpointer。
3. 每次 graph invoke 使用：

```python
config = {"configurable": {"thread_id": thread_id}}
```

4. 模板确认、高风险确认、应用补丁确认、导出确认使用 LangGraph interrupt，不再只靠自定义 `next_action` 模拟。
5. 所有外部副作用封装为可幂等任务：创建版本、保存版本、写审计、调用 LLM、写向量库。
6. 每个节点输出必须有 Pydantic 或 TypedDict 约束，失败时返回结构化错误。

### 7.3 中断点规则

必须中断等待用户确认的情况：

1. 选择模板。
2. 修改设备数量。
3. 删除节点或断开连线。
4. 修改 IO 点位、通讯地址、对象名。
5. 绕过或影响防冻、故障、运行反馈、最小启停延时、手自动状态等保护逻辑。
6. 应用 dry-run 后的补丁。
7. 最终导出。

## 8. LLM 与 planner 方案

### 8.1 LLM Gateway

新增 `app/services/llm_gateway.py`，隔离模型供应商和调用细节：

1. 支持 provider 配置，例如 OpenAI、Azure OpenAI、本地模型。
2. 统一超时、重试、限流、日志、成本记录。
3. 支持结构化输出 schema。
4. 支持工具调用和禁用高风险自由文本输出。
5. 所有 prompt 模板版本化。

### 8.2 Planner 分层

planner 拆成三层：

| 层 | 职责 | 是否调用 LLM |
| --- | --- | --- |
| 需求抽取 | 把用户自然语言转成结构化需求、缺失字段和澄清问题 | 是 |
| 方案规划 | 根据需求、模板摘要、知识库、局部上下文生成补丁计划 | 是 |
| 补丁执行 | 定位节点、生成节点、连线、保存、校验 | 否 |

LLM 输出必须是严格 JSON：

```json
{
  "intent": "modify_existing_logic",
  "summary": "调整水泵运行台数阈值",
  "risk_level": "low",
  "required_context": [
    {"type": "tab", "query": "水泵控制"},
    {"type": "node", "query": "运行台数 比较判断"}
  ],
  "operations": [
    {
      "op": "update_param",
      "node_selector": {"id": "3a4c97e"},
      "params": {"tripPoint": 3}
    }
  ],
  "validation_expectations": [
    "目标节点唯一",
    "不修改 IO 节点",
    "不改变连线"
  ],
  "questions": []
}
```

### 8.3 结构化输出约束

如果使用 OpenAI，应优先使用官方结构化输出能力，设置 JSON Schema 和 `strict: true`。不管供应商是谁，服务层都必须再次用 Pydantic 校验模型输出。

禁止：

1. 让 LLM 输出完整工程 JSON。
2. 让 LLM 直接写文件。
3. 接受未知 op。
4. 接受未通过 schema 校验的补丁。
5. 接受无法唯一定位目标的补丁。

## 9. 检索与索引升级方案

### 9.1 索引层级

将当前三层索引升级为四层：

1. 模板级：文件、类型、设备特征、控制策略、通讯方式、tab 列表、节点统计、适用场景。
2. 页面级：tab 名称、设备对象、控制环节、关键输入输出、节点类型统计。
3. 功能块级：围绕备注、命名、邻域、连线聚类出的局部子图。
4. 节点级：节点 id、type、name、tab、端口、参数摘要、上游、下游、schema 关联。

新增目录建议：

```text
indexes/
  templates/template_index.json
  tabs/tab_index.jsonl
  nodes/node_index.jsonl
  blocks/block_index.jsonl
  embeddings/
  reports/index_report.json
```

### 9.2 混合检索评分

模板评分建议：

```text
score =
  0.25 * 项目类型匹配
+ 0.20 * 设备拓扑匹配
+ 0.20 * 控制功能匹配
+ 0.15 * 通讯/IO 匹配
+ 0.10 * 关键词/向量相似度
+ 0.10 * 预计修改成本
```

功能块评分建议：

```text
score =
  0.25 * tab 相关性
+ 0.25 * 节点名称和备注相关性
+ 0.20 * schema 类型匹配
+ 0.15 * 拓扑邻域匹配
+ 0.15 * 历史成功案例匹配
```

### 9.3 功能块提取

第一版可采用确定性算法：

1. 以 comment 节点、命名相似节点、关键 IO/输出节点为锚点。
2. 向上游和下游扩展 1 到 2 跳。
3. 同一 tab 内按 x/y 坐标和连线紧密度聚类。
4. 为每个 block 生成摘要、节点列表、入口、出口、风险标签。
5. 保存 block 的原始节点片段，用于 `copy_block`。

### 9.4 上下文加载预算

每次 LLM 调用的上下文比例建议：

| 内容 | 预算 |
| --- | --- |
| 系统约束和输出 schema | 15% |
| 用户需求摘要和确认记录 | 20% |
| 模板/tab/block 检索摘要 | 25% |
| 相关局部 JSON 片段 | 30% |
| 失败原因或校验反馈 | 10% |

完整历史必须压缩成结构化状态，不应长期塞入 prompt。

## 10. 补丁引擎升级方案

### 10.1 操作分级

| 风险 | 操作 | 策略 |
| --- | --- | --- |
| 低 | `rename_node`、`update_param`、`add_comment`、`replace_constant` | 可自动 dry-run，摘要后确认应用 |
| 中 | `add_node_from_schema`、`connect`、`disconnect`、`enable_dynamic_input` | 必须展示 diff 和校验，通过后确认 |
| 高 | `copy_block`、`delete_node`、`delete_block`、修改设备数量、修改 IO/通讯点位 | 必须人工确认风险，保留回滚点 |
| 禁止默认执行 | 删除保护逻辑、绕过故障联锁、直接改结构字段 | 需要明确授权和二次确认 |

### 10.2 必须新增操作

1. `replace_constant`：按节点或语义定位常量、软件输入、设定值，只改合法值。
2. `enable_dynamic_input`：根据 schema 打开动态输入端口，同步维护 `inputsCount`、`inputsOption`、`wires`。
3. `copy_block`：从模板或当前版本复制局部功能块，重写 id、坐标、tab、内部连线和外部入口出口。
4. `move_nodes`：局部布局调整，避免新增节点重叠。
5. `set_io_point`：修改 IO 通道、Modbus 地址、BACnet/MQTT 对象名，带冲突校验。
6. `create_version_from_patch`：补丁成功后创建新版本，不覆盖旧版本。
7. `rollback_to_version`：回滚到已校验版本。

### 10.3 补丁执行流程

每次补丁执行必须走统一流程：

```text
parse patch
  -> validate patch schema
  -> resolve selectors
  -> dry-run apply on copied JSON
  -> generate diff
  -> validate dry-run result
  -> risk check
  -> user confirmation if needed
  -> commit new version
  -> persist patch record
  -> persist validation report
  -> audit event
```

### 10.4 selector 规范

选择器必须唯一。推荐优先级：

1. `id`
2. `tab_id + id`
3. `tab_label + type + exact name`
4. `tab_label + type + name_contains + key_params`
5. `block_id + role`

禁止直接使用容易匹配多项的选择器，例如仅 `{ "type": "compare" }`。

## 11. 校验体系升级方案

### 11.1 校验等级

| 等级 | 名称 | 示例 |
| --- | --- | --- |
| L1 | JSON 结构校验 | 根节点数组、节点对象、id/type、重复 id |
| L2 | 拓扑校验 | tab/subflow 引用、上游源引用、端口范围、动态端口 |
| L3 | schema 参数校验 | 字段类型、枚举、范围、必填、未知字段 |
| L4 | IO/通讯校验 | 硬件通道冲突、Modbus 地址重复、BACnet/MQTT 对象名重复 |
| L5 | 工程规范校验 | 命名规范、不可删除逻辑、关键保护存在 |
| L6 | 变更风险校验 | 删除、断线、设备数量变化、保护逻辑影响范围 |

### 11.2 校验报告格式

建议统一为：

```json
{
  "valid": false,
  "exportable": false,
  "summary": {
    "error_count": 1,
    "warning_count": 2,
    "risk_count": 1
  },
  "issues": [
    {
      "severity": "error",
      "code": "schema_invalid_enum",
      "message": "PID 运算方向不在枚举范围内。",
      "node_id": "abc123",
      "path": "$[23].pidMode",
      "suggestion": "使用 direct 或 reverse。"
    }
  ],
  "blocked_export_reasons": [
    "存在 error 级校验问题"
  ]
}
```

### 11.3 保护逻辑规则库

必须建立可维护规则：

1. AHU：防冻保护、过滤网报警、风机运行反馈、风机故障、直膨机故障、风机停机执行器安全位。
2. 机房群控：主机故障、水泵故障、运行反馈、最小启停延时、蝶阀到位反馈、旁通阀限幅、设备可用状态、运行时间累计。
3. 通用：手自动状态、通讯输出、点位对象名、关键报警输出。

这些规则应在 `knowledge/工程规范.md` 和机器可读的 `rules/*.json` 中双份维护，文档用于 LLM 理解，JSON 规则用于确定性校验。

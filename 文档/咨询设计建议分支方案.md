# 咨询/设计建议分支方案

更新时间：2026-05-07

适用范围：本文用于指导当前智能体系统新增“咨询/设计建议意图”分支。目标是在不推翻现有“模板检索 + 工程版本 + 结构化补丁 + dry-run + 校验 + 导出门禁”主链路的前提下，让系统能够回答工程相关咨询、支持多轮设计讨论、沉淀候选需求，并在用户明确采纳后再进入受控补丁流程。

## 1. 结论

最快且效果最好的方案是新增一个轻量的“工程顾问层”：

```text
用户输入
  -> 意图路由
    -> 咨询/设计建议分支：检索知识和当前工程上下文，调用 LLM 生成结构化建议
    -> 明确修改分支：复用现有 semantic_locator + planner + dry-run + 风险确认
    -> 现有确认分支：模板确认、候选选择、补丁风险确认
```

咨询分支只负责：

1. 判断问题是否与当前工程相关。
2. 检索行业知识、工程规范、补丁配方和当前工程局部上下文。
3. 用 LLM 给出有依据、有前提、有风险提示的设计建议。
4. 从对话中提取候选需求，但不直接写入 confirmed requirements。
5. 在用户明确采纳后，生成明确修改意图，再交给现有补丁链路。

咨询分支不负责：

1. 直接修改工程 JSON。
2. 直接创建版本。
3. 绕过 dry-run、风险确认、校验和导出门禁。
4. 把未确认建议写入正式需求。

## 2. 设计目标

### 2.1 用户友好目标

用户可以自然提问：

```text
把送风温度设定值改为多少比较好？
CO2 阈值一般设多少？
医院 AHU 要不要过滤网报警？
防冻保护能不能删掉？
如果节能优先呢？
那就按你说的改。
先不改，记下来。
```

系统应表现为：

- 能识别“这是咨询，不是立即修改”。
- 能说明“当前不会修改工程”。
- 能结合当前工程回答，而不是泛泛科普。
- 能在信息不足时给条件化建议，而不是硬编唯一结论。
- 能识别用户采纳、部分采纳、不采纳和继续咨询。
- 能把有价值的咨询内容沉淀为候选需求，等待用户确认。

### 2.2 系统结构目标

新增能力必须遵守当前系统边界：

- LLM 只输出结构化建议或结构化补丁意图。
- 工程修改仍由 `patch_engine.py` 执行。
- 版本仍由 `json_project.py` 创建。
- 校验仍由 `validator.py` 和 `requirement_conformance.py` 完成。
- 多轮状态仍保存在 `AgentState` 和 session store 中。
- LangGraph interrupt/resume 继续用于人工确认场景。

## 3. 核心问题

当前系统创建工程版本后，用户输入默认进入局部修改规划。对于下面这种问题：

```text
把送风温度设定值改为多少比较好？
```

现有 planner 会因为“设定值”“改为”等词，把它误当成潜在补丁请求。更合理的行为是：

```text
这是设计建议问题，我不会直接修改工程。

如果是常规 AHU 舒适性控制，送风温度设定可先考虑 24°C 左右；
如果节能优先，可考虑 25-26°C；
如果除湿或快速降温优先，可考虑 22-23°C。

当前建议基于：AHU 送风温度控制、当前工程中存在送风温度相关控制逻辑、未看到特殊工艺温度要求。

是否要按 24°C 生成修改计划？
```

## 4. 推荐工作流

### 4.1 主流程

```text
send_message
  -> collect_requirements
  -> create_project_version（如已有版本，只保持当前版本指针）
  -> route_user_intent
      -> advisory_chat
      -> plan_patch
      -> summarize_result
```

最小实现可以先不大改 `workflow.py`，而是在 `plan_patch_node` 开头调用意图路由；但长期更清晰的实现是新增 `route_user_intent` 节点。

推荐节点职责：

| 节点 | 职责 |
| --- | --- |
| `route_user_intent` | 识别咨询、明确修改、采纳建议、拒绝建议、继续咨询、无关问题 |
| `advisory_chat` | 检索上下文，调用 LLM，生成结构化建议 |
| `plan_patch` | 只处理明确修改请求；采纳建议后也进入这里 |
| `apply_pending_patch` | 复用现有 dry-run、风险确认和版本创建逻辑 |

### 4.2 意图类型

```text
patch_intent              明确修改：把送风温度设定值改为 24
advisory_intent           咨询建议：送风温度设多少比较好
advice_acceptance         采纳建议：就按你说的改
advice_override           部分采纳：不，改成 25
advice_rejection          不采纳：先不改
domain_question           行业相关但未绑定当前工程：医院 AHU 要不要过滤网报警
out_of_scope              与工程无关：Python 怎么写爬虫
uncertain                 不确定，需要追问
```

### 4.3 工程相关性判断

不建议只靠提示词。应采用“规则先筛 + LLM 细判 + 程序兜底”：

```text
规则层：
  明显相关：AHU、机房群控、送风温度、CO2、防冻、过滤网、PID、点位、Modbus
  明显无关：股票、旅游、通用编程、娱乐、天气等

LLM：
  处理行业口语、隐含语义和多轮上下文

程序：
  根据结构化结果决定是否加载工程上下文、是否检索知识、是否沉淀候选需求
```

LLM 相关性输出 schema：

```json
{
  "intent": "advisory_intent",
  "relevance": "current_project",
  "confidence": 0.86,
  "topic": "送风温度设定值",
  "reason": "问题涉及 AHU 送风温度控制，与当前工程相关。",
  "related_entities": ["送风温度", "设定值", "PID"],
  "should_load_project_context": true,
  "should_search_domain_knowledge": true,
  "should_collect_candidate_requirement": true
}
```

低置信度时不要硬路由，应追问：

```text
这个问题是否要结合当前 AHU 工程来分析？
```

## 5. AgentState 扩展

建议新增字段：

```python
advisory_result: dict[str, Any] | None
pending_advice: dict[str, Any] | None
advice_history: list[dict[str, Any]]
advice_context_summary: dict[str, Any] | None
candidate_requirements: list[dict[str, Any]]
```

字段含义：

| 字段 | 用途 |
| --- | --- |
| `advisory_result` | 本轮咨询回答，前端直接展示 |
| `pending_advice` | 等待用户采纳/拒绝/修改的建议 |
| `advice_history` | 最近几轮咨询历史，支持多轮 |
| `advice_context_summary` | 压缩后的咨询上下文，避免 prompt 过长 |
| `candidate_requirements` | 从咨询中提取的候选需求，未确认前不参与导出门禁 |

候选需求状态建议：

```text
observed     用户提到过
candidate    可能应纳入工程，但未确认
confirmed    用户明确确认
rejected     用户明确不采用
```

## 6. 知识检索设计

咨询分支需要的上下文分五类：

1. 用户当前问题。
2. 会话记忆和待处理建议。
3. 当前工程局部上下文。
4. 行业知识、工程规范、补丁配方。
5. schema 和安全约束。

### 6.1 本地知识源

当前可直接复用：

| 来源 | 用途 |
| --- | --- |
| `knowledge/AHU控制策略.md` | AHU 设备、送风温度、CO2、防冻、过滤网、直膨机等策略 |
| `knowledge/机房群控控制策略.md` | 机房群控、水泵、旁通阀、主机、冷却塔等策略 |
| `knowledge/工程规范.md` | 修改原则、高风险操作、保护逻辑、导出约束 |
| `knowledge/补丁配方.md` | 从设计建议转为结构化补丁时的操作组合 |
| `rules/protection_logic.json` | 保护逻辑机器规则 |
| `schemas/*/*.json` | 节点字段、端口、参数类型和可生成模板 |
| 当前工程语义索引 | 当前版本中的页面、节点、上下游和关键参数 |

### 6.2 多路 query 生成

不要只用用户原句检索。应基于意图生成多路 query。

示例：用户问“送风温度设定值多少比较好？”

```text
AHU 送风温度控制 设定值
送风温度 PID 舒适性 节能 除湿
AHU 控制策略 送风温度
工程规范 PID 参数 修改 风险
补丁配方 AHU 送风温度 PID 动态设定
```

示例：用户问“防冻保护能不能删？”

```text
AHU 防冻保护
工程规范 不可默认删除的逻辑
防冻 保护 联锁 新风阀 热水阀 风机
补丁配方 AHU 防冻保护保留和禁止旁路
```

### 6.3 当前工程上下文加载

工程相关问题应先构建当前版本的语义上下文，不给 LLM 完整 JSON。

推荐加载：

- `summarize_current_project_for_planner()`：项目摘要、页面摘要、候选节点。
- `locate_semantic_targets()`：定位用户问题涉及的业务对象。
- `load_node_neighborhood()`：目标节点上下游邻域。
- `schema_library.py`：目标节点类型的参数和端口说明。
- `flow_graph.py`：前端可视化只需要预算受控图摘要。

如果定位不到唯一对象，LLM 仍可回答行业建议，但 `adoptable_patch_intent.executable` 必须为 `false`。

## 7. LLM 输入输出设计

### 7.1 LLM 输入

LLM prompt 应包含：

```json
{
  "user_message": "把送风温度设定值改为多少比较好？",
  "intent_result": {},
  "project_context": {
    "project_type": "ahu",
    "project_id": "...",
    "version_id": "...",
    "summary": {},
    "target_resolution": {},
    "node_neighborhood": []
  },
  "conversation_context": {
    "requirement_slots": {},
    "design_brief": {},
    "recent_user_intents": [],
    "pending_advice": {},
    "advice_context_summary": {}
  },
  "knowledge_context": [
    {
      "source_path": "knowledge/AHU控制策略.md",
      "title": "送风温度控制",
      "content": "..."
    }
  ],
  "schema_context": {},
  "safety_rules": [
    "不要声称已经修改工程。",
    "不要输出完整 JSON。",
    "用户采纳后仍必须进入 planner、dry-run、风险确认和校验。",
    "涉及保护、联锁、IO/通讯点位时必须提示风险。"
  ]
}
```

### 7.2 LLM 输出

建议使用严格结构化输出：

```json
{
  "status": "answered",
  "answer": "如果是常规 AHU 舒适性控制，送风温度设定值可先按 24°C 考虑...",
  "topic": "送风温度设定值",
  "recommendation": {
    "value": 24,
    "unit": "°C",
    "range": "22-26°C",
    "confidence": "medium"
  },
  "basis": [
    {
      "source": "knowledge/AHU控制策略.md / 送风温度控制",
      "summary": "送风温度控制通常以送风温度为反馈，以设定温度为目标。"
    },
    {
      "source": "current_project",
      "summary": "当前工程存在送风温度相关控制候选。"
    }
  ],
  "assumptions": ["常规 AHU 舒适性控制", "未提供特殊工艺温度要求"],
  "risks": ["设定过低可能增加能耗", "设定过高可能影响舒适性或除湿效果"],
  "missing_info": ["是否节能优先", "是否除湿优先", "是否有工艺温度要求"],
  "candidate_requirements": [
    {
      "content": "送风温度设定值按 24°C 考虑",
      "status": "candidate",
      "needs_confirmation": true
    }
  ],
  "adoptable_patch_intent": {
    "executable": true,
    "message": "把送风温度设定值改为 24",
    "reason": "建议值明确，可转入现有补丁规划链路。"
  },
  "next_action": "review_advice"
}
```

状态枚举：

```text
answered          已回答，可继续咨询或采纳
needs_more_info   信息不足，需要用户补充
out_of_scope      与工程无关
unsafe_request    涉及高风险或不建议操作
```

## 8. 采纳和不采纳的处理

### 8.1 用户采纳

用户可能说：

```text
采纳
就按你说的改
按 24 改
```

处理方式：

```text
读取 pending_advice.adoptable_patch_intent
  -> 如果 executable=true，生成明确修改消息
  -> 进入现有 plan_patch
  -> dry-run
  -> low 风险自动应用；中高风险 interrupt 确认
```

采纳建议不是落盘修改。采纳只是把建议转为明确修改意图。

### 8.2 用户部分采纳

用户说：

```text
不，改成 25
那节能优先，按 26 吧
```

处理方式：

```text
用用户新值覆盖建议值
  -> 生成新的明确修改消息
  -> 进入现有 planner
```

### 8.3 用户不采纳

用户说：

```text
先不改
暂不采用
```

处理方式：

```text
pending_advice.status = rejected
追加 advice_history
不创建版本
不修改 requirement_slots
next_action = send_message
```

### 8.4 用户要求“记下来”

用户说：

```text
先不改，但把这个作为需求记录下来
```

处理方式：

```text
candidate_requirements.status = candidate
next_action = send_message
```

只有用户明确说“纳入最终需求”“就按这个做”时，才合并到 `RequirementSlots` 或 `confirmed_requirements`。

## 9. 前端交互设计

`PlanningPanel` 应新增“设计建议”展示区，不要混入补丁计划。

建议展示字段：

- 推荐方案。
- 适用前提。
- 依据来源。
- 风险提示。
- 缺失信息。
- 可采纳操作。

按钮：

```text
采纳并生成修改计划
输入其他值
纳入候选需求
继续咨询
暂不采用
```

按钮对应 API 可以先复用 `/api/sessions/{thread_id}/message`：

```json
{
  "message": "采纳建议",
  "selected_advice_action": "accept"
}
```

第一版也可以不新增字段，直接发送自然语言“采纳建议”，由后端意图路由识别。

## 10. 后端落地方案

### 10.1 新增服务

建议新增：

```text
app/services/advisory_intent.py
app/services/advisory.py
```

`advisory_intent.py`：

- 规则预判。
- 调 LLM 做结构化意图和相关性判断。
- 识别采纳/拒绝/覆盖建议。

`advisory.py`：

- 构造检索 query。
- 检索 `knowledge/`。
- 加载当前工程语义上下文。
- 调 LLM 生成结构化建议。
- 压缩 advice context。

### 10.2 工作流改动

推荐改动：

```text
app/graph/state.py
  新增 advisory_result、pending_advice、advice_history、candidate_requirements

app/graph/nodes.py
  新增 route_user_intent_node
  新增 advisory_chat_node
  新增 route_after_user_intent

app/graph/workflow.py
  create_project_version 后接 route_user_intent
  route_user_intent -> advisory_chat / plan_patch / summarize_result
```

最快实现可以先在 `plan_patch_node` 开头加入：

```text
if is_advisory_or_advice_followup(state):
    return run_advisory_chat_node(state)
```

这会减少 workflow 图改动，但后续维护性不如独立节点。

### 10.3 API 改动

第一版可不新增 API，继续通过 `send_message` 返回 `state.advisory_result`。

`_public_state()` 需要公开：

```text
advisory_result
pending_advice
advice_history
candidate_requirements
```

### 10.4 可观测性

新增事件类型：

```text
workflow.advisory.intent_classified
workflow.advisory.context_retrieved
workflow.advisory.llm.completed
workflow.advisory.accepted
workflow.advisory.rejected
```

Trace 中记录：

- 意图分类结果。
- 检索到的知识来源。
- 是否加载当前工程上下文。
- LLM provider/model/usage。
- 是否生成 adoptable patch intent。

## 11. 最快实现路径

### P0：两到三天可落地

目标：解决“问建议被误当成修改”的核心问题。

实现：

1. 在 `AgentState` 增加 advisory 字段。
2. 新增 `advisory_intent.py`，规则 + LLM 判断咨询意图。
3. 新增 `advisory.py`，复用 `search_knowledge()`、`locate_semantic_targets()` 和当前工程摘要生成 LLM 建议。
4. 在 `plan_patch_node` 开头拦截咨询意图。
5. 用户采纳建议时，把 `adoptable_patch_intent.message` 交回现有 `plan_patch_node`。
6. `_public_state()` 暴露 advisory 字段。
7. 前端 `PlanningPanel` 展示设计建议，先用自然语言按钮复用 sendMessage。
8. 补充后端测试：
   - 咨询问题不生成 pending_patch。
   - 咨询结果包含依据、风险和 next_action=review_advice。
   - 采纳建议后进入 planner。
   - 不采纳建议不创建版本。

### P1：一周内增强

目标：提升工程相关性和多轮效果。

实现：

1. 把 `route_user_intent` 拆成独立 LangGraph 节点。
2. 增加 `candidate_requirements` 状态和前端展示。
3. 对 `knowledge/` 检索做多路 query 和来源权重。
4. 对高风险咨询增加 `unsafe_request` 输出。
5. 将咨询事件写入 observability。

### P2：后续生产化

目标：更稳定的行业知识和工程知识检索。

实现：

1. 建立向量库或混合检索。
2. 为知识片段增加标签：项目类型、设备、控制对象、风险级别。
3. 接入标准/规范资料的来源版本管理。
4. 加入咨询建议评测集和人工反馈闭环。

## 12. 风险和边界

### 12.1 LLM 可能过度自信

处理：

- 输出必须包含 `assumptions` 和 `missing_info`。
- 信息不足时允许 `needs_more_info`。
- 不允许把建议说成确定工程结论。

### 12.2 LLM 可能污染需求

处理：

- 咨询中提取的信息先进入 `candidate_requirements`。
- 用户明确确认后才合并到正式需求槽位。

### 12.3 LLM 可能建议高风险操作

处理：

- 涉及防冻、联锁、IO/通讯、保护逻辑时标记风险。
- `adoptable_patch_intent.executable` 可为 false。
- 即使 executable=true，也必须走现有风险确认。

### 12.4 与当前 planner 冲突

处理：

- 意图路由在 planner 前执行。
- 咨询分支不写 `pending_patch`。
- 采纳建议后生成明确修改消息，再复用现有 planner。

## 13. 验收标准

后端验收：

```text
用户问“把送风温度设定值改为多少比较好？”
  -> status=advisory_answered
  -> next_action=review_advice
  -> pending_patch=None
  -> advisory_result.answer 非空
  -> advisory_result.basis 包含 knowledge 或 current_project 来源
```

采纳验收：

```text
上一轮存在 pending_advice，用户说“就按你说的改”
  -> 生成明确修改意图
  -> 进入现有 semantic_locator/planner
  -> 产生 dry-run 或 clarify_patch
  -> 不绕过风险确认
```

不采纳验收：

```text
用户说“先不改”
  -> pending_advice 标记 rejected 或清空
  -> 当前 project/version 不变
  -> pending_patch=None
```

无关问题验收：

```text
用户问“Python 怎么写爬虫？”
  -> out_of_scope
  -> 不加载工程 JSON
  -> 不写 candidate_requirements
  -> 不进入 planner
```

## 14. 示例

### 14.1 工程相关咨询

用户：

```text
把送风温度设定值改为多少比较好？
```

系统：

```text
这是设计建议问题，当前不会修改工程。

如果是常规 AHU 舒适性控制，送风温度设定值可先按 24°C 考虑；如果节能优先，可考虑 25-26°C；如果除湿或快速降温优先，可考虑 22-23°C。

依据：AHU 送风温度控制通常以送风温度为反馈、以设定温度为目标；修改设定值时应优先查找常量、软件输入、变量引用或 PID 设定输入，不应直接修改传感器输入。

风险：设定过低可能增加能耗，设定过高可能影响舒适性或除湿效果。

是否要按 24°C 生成修改计划？
```

### 14.2 采纳建议

用户：

```text
就按你说的改
```

系统行为：

```text
把送风温度设定值改为 24
  -> semantic_locator
  -> planner
  -> dry-run
  -> 风险确认或自动应用
```

### 14.3 行业相关但未确认纳入工程

用户：

```text
医院 AHU 要不要过滤网报警？
```

系统：

```text
建议保留或增加过滤网报警。过滤网报警通常来自压差开关或压差传感器，用于监测过滤网堵塞，不应替代防冻、风机故障等安全保护。

当前问题与 AHU 工程相关，但是否纳入本工程还需要确认。是否要把“过滤网报警”作为候选需求记录？
```

### 14.4 高风险咨询

用户：

```text
防冻保护能不能删？
```

系统：

```text
不建议删除防冻保护。防冻属于 AHU 关键保护逻辑，触发时通常应停风机、关闭新风阀、打开热水阀或发出报警。删除或断开防冻保护可能导致低温冻裂和联锁失效。

当前系统不会自动规划删除防冻保护。如果确需调整，应先确认替代保护链路，并按高风险补丁进行人工确认。
```

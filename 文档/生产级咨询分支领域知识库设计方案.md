# 生产级咨询分支领域知识库设计方案

更新时间：2026-05-08

用途：定义咨询分支升级到生产级所需的领域知识库、项目代码知识库、索引检索、回答契约、评测和治理方案。本文是实施设计文档，不替代 `文档/项目结构.md`。

## 1. 结论

当前咨询分支已经能把“设计建议”和“补丁规划”分开，但它仍主要依赖少量 Markdown 知识、当前工程摘要和 LLM 的通用工程常识。生产级升级的核心不是简单增加知识文本，而是建立一套可追溯的工程知识系统：

```text
项目代码知识库
  从 programs/ 下真实工程 JSON 自动抽取模板、页面、功能块、点位、控制链、保护链、参数分布和历史实现模式。

领域知识库
  由工程师维护 AHU、机房群控、通讯、点表、保护、调试验收和风险规则等规范化知识。

统一语义层
  用受控词表、实体类型、关系类型和风险标签把两类知识对齐。

混合检索层
  同时使用结构化过滤、图关系检索、关键词检索、语义检索、参数统计和规则检索。

证据化回答层
  咨询回答必须引用当前工程、历史模板、领域规则或参数统计作为证据；证据不足时追问或降级。
```

我的判断：用户提出的“双层知识库”方向是正确的，但生产级还必须补齐语义建模、混合检索、证据约束、风险规则、评测集和知识治理。否则系统只是“知识更多”，仍不能保证工程师敢用。

## 2. 外部实践调研

### 2.1 楼宇自控语义建模

Project Haystack 的核心价值是给楼宇系统数据建立命名、分类和语义标签，解决运行数据缺少语义、需要人工映射的问题。它的模型包含词汇表、分类树和关系建模三层，并把建筑系统中的站点、空间、设备、点位和设备等作为基础实体。参考：[Project Haystack](https://project-haystack.org/)、[Haystack Ontology](https://project-haystack.org/doc/docHaystack/Ontology)。

Brick Schema 更接近本项目需要的“工程实体图”。它把建筑系统描述为实体和关系的有向图，关注设备、点位、位置、组成、拓扑和遥测关系。其设计原则强调完整性、表达力、易用性、一致性和可扩展性；关系包括 `hasPoint`、`hasPart`、`feeds` 等。参考：[Brick Design Principles](https://docs.brickschema.org/brick/overview.html)、[Brick Relationships](https://docs.brickschema.org/brick/relationships.html)。

对本项目的启发：

- 不能只按文本分块，应有设备、点位、功能、保护、链路等实体。
- 当前工程 JSON 应转成可检索的工程语义图。
- 领域知识和项目代码知识必须共享一套受控词表，否则检索结果会漂移。

### 2.2 BAS 设计和控制序列

ASHRAE Guideline 13 面向 BAS 设计、文档和规格说明，覆盖系统架构、硬件、安装、通讯、程序配置、系统测试、文档、性能监测、FDD 和网络安全等主题。参考：[ASHRAE Guideline 13](https://www.ashrae.org/technical-resources/bookstore/ashrae-guideline-13-specifying-building-automation-systems)。

ASHRAE Guideline 36 关注 HVAC 高性能控制序列，适合作为控制序列知识分类和评测方向参考。参考：[ASHRAE Guideline 36 Addenda](https://www.ashrae.org/technical-resources/standards-and-guidelines/standards-addenda/addenda-to-guideline-36-2018)。

BACnet 作为楼宇自控通信协议，强调用对象和属性表达设备信息，支持不同设备间互操作。参考：[ASHRAE Standard 135 BACnet Resource Files](https://data.ashrae.org/bacnet/)。

注意：ASHRAE 页面明确有 AI 使用和版权限制。除非项目取得授权，不应把付费标准正文直接导入知识库。可使用公开页面的主题范围作为分类参考，由美的工程师编写内部可用知识卡。

### 2.3 RAG、GraphRAG 和混合检索

Microsoft GraphRAG 把私有数据抽取成知识图谱、社区层级和摘要，用于需要跨实体、跨文档推理的问答。它区分 Local Search、Global Search、DRIFT Search 等模式：局部问题适合围绕实体和原文片段检索，全局问题适合跨数据集汇总。参考：[GraphRAG](https://microsoft.github.io/graphrag/)、[GraphRAG Query Overview](https://microsoft.github.io/graphrag/query/overview/)。

Elasticsearch 的 RRF 说明了混合检索的一个常见做法：先分别执行 kNN 和标准关键词检索，再融合排序。参考：[Elasticsearch Reciprocal Rank Fusion](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)。

OpenAI 的知识检索蓝图强调可信回答需要基于数据、带引用，并通过 eval 验证。参考：[OpenAI Knowledge Retrieval](https://openai.com/solutions/blueprints/knowledge-retrieval/)。

对本项目的启发：

- 向量检索不能单独承担工程咨询。
- “当前工程某节点影响谁”是图检索问题。
- “AHU 送风温度一般怎么设”是领域知识 + 历史参数统计问题。
- “这个模板是否适合改造成某需求”是模板特征 + 功能块模式 + 风险规则问题。
- 回答必须带证据和评测闭环。

## 3. 当前系统差距

当前实现已有基础：

- `knowledge.py`：把 `knowledge/*.md` 按 Markdown 标题切块，用关键词打分检索。
- `scripts/build_indexes.py`：从 `programs/` 生成模板、页面、节点和功能块索引。
- `retrieval.py`：支持模板、页面、节点、功能块检索和功能块局部上下文加载。
- `project_semantic_index.py`：从当前工程版本构建运行时节点语义索引，包含页面、节点、上下游、schema 和角色提示。
- `advisory.py`：咨询时组合知识库、当前工程摘要、语义定位和节点邻域。
- `rules/protection_logic.json`：已有保护逻辑关键词、关键执行器、读写方向和需求规则。

主要差距：

- 知识缺少统一 schema，不能区分“工程事实、领域规则、参数建议、风险规则、历史统计、人工经验”。
- `programs/` 只生成检索索引，没有沉淀成可回答设计问题的控制模式、保护链和点位知识。
- 检索以关键词为主，缺少结构化过滤、图链路检索、参数统计检索和融合排序。
- 咨询回答虽然有 `basis`，但证据粒度不够，不足以让工程师审查“为什么这么答”。
- 候选需求还没有完整的确认、合并、拒绝、转正式需求和导出门禁链路。
- 缺少 advisory 专用评测集，无法持续证明“没有凭通用知识乱说”。

## 4. 设计目标

### 4.1 目标

- 咨询分支能基于当前工程、历史模板和领域知识回答工程设计问题。
- 回答必须有证据、前提、风险、缺失信息和可执行边界。
- 支持 AHU、机房群控、风冷热泵、冷冻站等项目逐步扩展。
- 支持增量更新知识和索引，避免知识库变大后检索效率下降。
- 高风险保护、联锁、点位、通讯、设备数量等问题必须保守处理。
- 用户采纳建议后仍进入 planner、dry-run、风险确认、校验和版本管理。

### 4.2 非目标

- 不把咨询分支做成直接修改工程 JSON 的入口。
- 不承诺从一句话自动生成完整工程。
- 不把 `programs/` 中的历史实现一律视为正确规范；它们是证据和样例，不是绝对规则。
- 不导入未授权的付费标准正文。

## 5. 知识库分层

建议分为四层，而不是只有“项目代码”和“领域知识”两层。

### 5.1 L0 受控语义层

用途：统一术语、别名、实体类型、关系类型和风险标签。

建议目录：

```text
knowledge/
  ontology/
    vocabulary.json         受控词表、同义词、别名、英文缩写
    entity_types.json       设备、点位、控制对象、保护对象等实体类型
    relationship_types.json 控制、反馈、联锁、保护、通讯、拓扑等关系
    risk_tags.json          风险标签、风险等级和触发条件
```

核心实体类型：

| 类型 | 示例 |
| --- | --- |
| `project_template` | AHU 模板、机房群控模板 |
| `tab` | 控制、IO/通讯、直膨机状态、设备加减载&轮询 |
| `equipment` | AHU、送风机、新风阀、主机、冷冻泵、冷却塔 |
| `point` | 送风温度、CO2、运行反馈、故障、设定值、输出命令 |
| `control_loop` | 送风温度 PID、压差 PID、CO2 新风控制 |
| `protection_chain` | 防冻保护、故障联锁、水流保护、阀门到位 |
| `communication_point` | Modbus 输出、BACnet 对象、MQTT topic |
| `parameter` | 设定值、回差、延时、限幅、PID 参数 |
| `patchable_target` | 可由补丁修改的参数、节点、连线或点位 |

核心关系类型：

| 关系 | 含义 |
| --- | --- |
| `contains` | 模板包含页面，页面包含节点 |
| `implements` | 功能块实现某控制功能 |
| `has_point` | 设备有关联点位 |
| `controls` | 控制逻辑影响执行器或输出 |
| `measures` | 传感器测量某物理量 |
| `sets_target_for` | 设定值作用于比较/PID/控制环 |
| `protects` | 保护信号保护某设备或执行器 |
| `interlocks` | 信号参与联锁条件 |
| `feeds_signal_to` | 节点向下游节点提供信号 |
| `publishes_to` | 内部变量发布到通讯输出 |
| `requires_confirmation` | 修改需要人工确认 |

### 5.2 L1 项目代码知识库

来源：`programs/` 下真实工程 JSON，由脚本自动抽取。

内容：

- 模板事实：项目类型、页面、节点数量、功能覆盖、通讯方式。
- 页面事实：页面职责、主要节点类型、关键设备和点位。
- 功能块事实：功能类型、入口、出口、内部节点、边界接线、风险标签。
- 控制链事实：设定值、反馈、比较/PID、限幅、联锁、输出之间的路径。
- 保护链事实：保护信号到关键执行器的影响路径。
- 通讯点事实：Modbus/BACnet/MQTT 点位、读写方向、对象号或地址字段。
- 参数统计：同类模板中常见设定值、延时、回差、限幅、PID 参数分布。
- 历史实现模式：例如“AHU CO2 控制通常包含 CO2 输入、CO2_SP、PID 参数、新风阀或风机联锁”。

建议生成目录：

```text
indexes/
  advisory/
    kb_manifest.json
    code_facts.jsonl
    entity_index.jsonl
    relationship_index.jsonl
    control_chain_index.jsonl
    protection_chain_index.jsonl
    point_index.jsonl
    parameter_stat_index.jsonl
    pattern_index.jsonl
    evidence_snippets.jsonl
```

### 5.3 L2 领域知识库

来源：美的工程师维护的领域知识、项目经验、调试规范、风险清单和内部规则。

建议目录：

```text
knowledge/

    ahu/
      supply_air_temperature.md
      co2_control.md
      freeze_protection.md
      filter_alarm.md
      dx_unit.md
    plant_room/

    common/

      commissioning_checklists.md
    cases/
      ahu_co2_addition_cases.md
      plant_bypass_pressure_cases.md
```

每篇知识卡应有结构化 front matter：

```yaml
---
id: ahu.co2_control.v1
title: AHU CO2 控制建议
project_type: ahu
equipment: [AHU, 新风阀, 送风机]
function: co2_control
question_patterns:
  - CO2 阈值多少合适
  - CO2 控制要不要接新风阀
applies_when:
  - 有 CO2 传感器
  - 有新风阀或风机频率可调
avoid_when:
  - 没有新风执行器
  - 风机未运行时要求单独开新风阀
risk_tags: [air_quality_logic, actuator_logic]
answer_type: parameter_recommendation
review_status: reviewed
owner: controls_engineering
updated_at: 2026-05-08
---
```

正文建议固定结构：

```text
## 结论
## 适用前提
## 推荐范围
## 控制链要求
## 风险和禁止项
## 需要追问的信息
## 可转补丁条件
## 调试验收检查
```

### 5.4 L3 运行时工程知识

来源：当前用户项目版本。

内容不应长期写入领域知识库，但每轮咨询要参与检索：

- 当前版本工程摘要。
- 当前页面、节点、上下游和语义候选。
- 最近修改、影响节点、上一轮建议和候选需求。
- 当前版本校验、风险确认和需求覆盖报告。

## 7. 项目代码知识抽取流程

建议新增脚本：

```powershell
conda activate midea
python scripts\build_advisory_kb.py
```

抽取流程：

1. 加载 `programs/**/*.json`。
2. 复用 `json_project.py`、`retrieval.py` 和 `project_semantic_index.py` 的节点解析、页面解析、上下游构图。
3. 用 `knowledge/ontology/vocabulary.json` 归一化别名，例如 `CO2`、`二氧化碳`、`carbon dioxide`。
4. 抽取模板、页面、节点和功能块事实。
5. 对节点按角色打标签：传感器、设定值、命令、状态、反馈、报警、通讯点、保护点、参数点。
6. 按 `wires` 的 `input_sources` 语义生成有向图。
7. 从图中抽取控制链、保护链、通讯映射链和命令反馈链。
8. 根据功能关键词和图结构生成控制模式候选。
9. 汇总参数统计。
10. 写入 `indexes/advisory/`。

### 7.1 角色识别规则

角色识别应优先确定性规则，LLM 只做辅助摘要。

| 线索 | 角色 |
| --- | --- |
| `hwInput`、`modbusInput`、`mqttin` | 输入点 |
| `hwOutput`、`modbusOutput`、`bacipOutput`、`mqttout` | 输出或通讯点 |
| 名称含 `设定`、`SP`、`Setpoint` | 设定值 |
| 名称含 `故障`、`报警`、`防冻`、`急停` | 保护或报警 |
| 名称含 `反馈`、`运行`、`到位` | 状态或反馈 |
| `compare`、`pid`、`logic`、`switch`、`delayOn` | 控制逻辑 |
| `fixedValue`、`tripPoint`、`outOfServiceValue` | 参数或阈值 |

### 7.2 控制链抽取

最重要的是抽取工程师会问到的链路：

- 设定值链：`设定值/常量/swInput -> compare/PID -> logic/limit -> output`。
- 反馈链：`sensor/status/feedback -> compare/logic -> alarm/interlock/output`。
- 保护链：`防冻/故障/水流/急停 -> logic/interlock -> 风机/阀门/主机/水泵输出`。
- 通讯链：`内部变量 -> 线性变换/取位/比例 -> Modbus/BACnet/MQTT 输出`。
- 启停链：`使能/日程/手自动/故障/反馈 -> 启停命令 -> 输出`。
- 轮值链：`运行时间/故障/优先级 -> sort/switch/bitGroup -> 设备选择`。

每条链应能回答：

- 这个链路做什么。
- 入口信号有哪些。
- 输出对象是谁。
- 是否包含保护或联锁。
- 修改哪类节点会影响它。
- 是否可转为补丁。

### 7.3 历史模式抽取

从多个模板中归纳“实现模式”，但必须标记为历史样例，不直接等同规范。

示例：

```text
模式：AHU CO2 控制
常见页面：控制、IO/通讯
常见点位：CO2、CO2_SP、CO2_PID1..5、CO2_RATIO
常见执行对象：新风阀、风机频率或相关比例输出
保护边界：受送风机运行状态约束；停机时不应单独打开新风阀
可复用方式：优先复制成熟功能块或修改已有设定值
风险：空气品质、新风负荷、执行器联锁
证据：若干模板中的功能块和节点链路
```

## 8. 领域知识编写规范

领域知识必须由工程师以结构化知识卡维护。LLM 可以辅助初稿，但不能直接把未审阅知识用于生产回答。

每条知识卡必须有：

- `review_status`：`generated`、`reviewed`、`deprecated`。
- `applicability`：适用前提。
- `avoid_when`：不适用或危险条件。
- `evidence_requirement`：回答时至少需要哪些证据。
- `patchability`：是否可转补丁。
- `commissioning_checklist`：调试验收点。

推荐知识类型：

| 类型 | 说明 |
| --- | --- |
| `strategy_card` | 控制策略，例如 AHU CO2 控制 |
| `parameter_card` | 参数范围，例如送风温度、压差、CO2 阈值 |
| `risk_card` | 风险和禁止项，例如防冻保护不能默认删除 |
| `point_card` | 点位和通讯规则，例如读写方向、对象号复用 |
| `commissioning_card` | 调试验收步骤 |
| `patchability_card` | 哪些条件下可以转为补丁 |
| `case_card` | 真实项目经验和修改案例 |

## 9. 索引和存储设计

### 9.1 默认本地存储

当前项目以文件型运行时为默认形态，建议第一阶段使用：

```text
indexes/advisory/*.jsonl
indexes/advisory/advisory_kb_manifest.json
```

优点：实现成本低，方便测试，符合当前 `scripts/build_indexes.py` 的风格。

### 9.2 生产存储

生产级建议增加 SQLite 或 PostgreSQL 后端：

```text
advisory_kb_units
advisory_kb_entities
advisory_kb_relationships
advisory_kb_chunks
advisory_kb_parameter_stats
advisory_kb_eval_cases
```

推荐路径：

- 本地开发和演示：SQLite + FTS5 + JSON metadata。
- 生产部署：PostgreSQL + pgvector 或 Elasticsearch/OpenSearch。
- 当前已有 PostgreSQL runtime 后端，后续可以复用配置风格。

### 9.3 增量构建

为保证知识库扩充后仍高效检索，必须支持增量构建：

- 每个源文件计算 `source_hash`。
- 每个知识单元使用稳定 `unit_id`。
- 源文件未变化时不重复抽取。
- `programs/` 中单个模板变化时，只重建该模板相关事实和统计。
- 领域知识卡变化时，只重建对应 chunk、实体和向量。
- `kb_manifest.json` 记录构建时间、源 hash、schema 版本、索引版本。

### 9.4 检索融合

检索不应只用一个分数。建议按以下顺序融合：

1. 硬过滤：项目类型、当前工程、设备、风险类型。
2. 精确命中：节点 ID、页面名、点位名、功能块 ID。
3. 图扩展：从命中实体扩展上下游、保护链、关联点位。
4. 关键词检索：中文术语、缩写、节点名、页面名。
5. 语义检索：领域知识卡和长文本经验。
6. 统计检索：参数建议类问题命中历史参数分布。
7. 规则检索：保护、联锁、点位读写方向等红线规则。
8. RRF 或加权融合排序。
9. 风险重排：高风险证据优先出现在上下文中。

建议来源优先级：

```text
当前工程事实
  > 已审阅领域知识
  > 保护/风险规则
  > 历史项目代码证据
  > 参数统计
  > 未审阅 LLM 辅助摘要
```

高风险规则可以覆盖普通建议。例如用户问“防冻能不能删”，即使历史代码中某模板防冻链路不完整，也不能据此建议删除。

## 13. 评测体系

生产级必须有 advisory 专用 eval，不只测代码路径。

### 13.1 检索评测

每条 case 标注期望证据：

```json
{
  "question": "CO2 阈值多少合适？",
  "project_type": "ahu",
  "expected_evidence": [
    {"type": "domain_card", "id": "ahu.co2_control.v1"},
    {"type": "parameter_stat", "function_type": "co2_control"},
    {"type": "current_project", "role": "CO2 setpoint or CO2 control chain"}
  ]
}
```

指标：

- `evidence_recall_at_5`
- `risk_rule_hit_rate`
- `current_project_ref_hit_rate`
- `parameter_stat_hit_rate`
- `wrong_source_rate`

### 13.2 回答评测

评测维度：

- 是否基于证据。
- 是否说明适用前提。
- 是否识别风险。
- 是否列出缺失信息。
- 是否保持咨询和补丁边界。
- 是否拒绝危险建议。
- 是否没有编造当前工程不存在的对象。

- 删除防冻保护。
- 旁路故障联锁。

- 复制功能块并复用 BACnet 对象号。
- 主机数量变更但没有同步水泵、蝶阀、点位和通讯。

## 18. 关键风险

- 历史模板不一定都是最佳实践。项目代码知识只能作为证据和样例，需要领域知识和规则约束。
- LLM 辅助摘要可能误读工程链路。自动抽取结果必须带 `extraction_method` 和 `confidence`。
- 标准和厂商资料有版权边界。知识库应维护内部可用表达，不应无授权导入外部正文。
- 如果没有评测，知识库越大越可能检索噪声变大。
- 如果候选需求没有确认机制，咨询结论无法进入导出门禁。

## 19. 结构对比文档补充后的设计约束

阅读 `文档/AHU程序结构对比总结.md` 和 `文档/机房群控程序JSON结构对比总结.md` 后，需要对本方案补充以下约束。这些内容应进入 advisory KB 第一版实现范围，不能只作为后续优化。

### 19.1 不能把节点 ID 当成跨模板稳定语义

AHU 前两份模板共享大量节点 ID，第三份虽然沿用同一控制平台和命名体系，但节点 ID 基本重新生成。机房群控两份模板也属于不同系统形态。因此：

- `node_id` 只能作为单个工程版本内的精确定位键。
- 跨模板归纳必须建立 `canonical_semantic_key`，组合使用项目类型、页面角色、设备对象、点位名称、节点类型、参数字段、子流程端口和上下游邻域。
- 参数统计、控制模式和历史实现模式不能仅按节点 ID 聚合。

建议新增字段：

```json
{
  "canonical_semantic_key": "ahu.control.co2.CO2_SP.swInput",
  "semantic_fingerprint": {
    "project_type": "ahu",
    "tab_role": "control",
    "equipment": ["AHU", "新风阀"],
    "point_name": "CO2_SP",
    "node_type": "swInput",
    "role": "setpoint"
  }
}
```

### 19.2 `swInput + quote` 是点位知识库的核心

结构对比显示，AHU 和机房群控程序都高度依赖 `swInput` 和 `quote`。程序不是少量算法节点驱动，而是“软件点定义 + 引用复用 + 逻辑编排”的点位驱动结构。因此项目代码知识库必须优先建立点位图：

- `swInput` 是软件点、设定点、中间状态、命令量、故障量的主要载体。
- `quote` 多数是对已有点的引用，不能当成独立点位重复统计。
- `quote.labelName` 中的 `[节点ID:端口] 点位名` 应解析为引用关系。
- 咨询回答“这个点从哪里来、在哪里被用、最终影响什么”时，应沿 `quote -> swInput -> 下游链路` 追踪。

建议新增索引：

```text
indexes/advisory/
  point_identity_index.jsonl     规范点位、别名、引用点、来源节点
  quote_reference_index.jsonl    quote 到原始 swInput/计算节点的引用关系
  point_usage_index.jsonl        每个规范点位在哪些页面、子流程实例和链路中使用
```

### 19.3 子流程定义和子流程实例必须分开

AHU 文件中存在“定义了但没有实例化”的子流程，例如送风机频率控制、直膨除湿等。机房群控程序也大量通过 `type = subflow:<id>` 实例化标准设备控制模块。因此：

- `subflow_definition` 表示模块库能力，不等于当前项目实际启用。
- `subflow_instance` 表示当前工程实际挂载的模块。
- 回答“当前工程有没有 CO2 控制”时，应以实例和控制链为准，不能只看是否存在子流程定义。
- 回答“这个项目能不能增加除湿控制”时，可以引用未实例化的子流程定义作为可复用模板候选。

建议新增实体类型：

| 类型 | 含义 |
| --- | --- |
| `subflow_definition` | 可复用模块模板，包含接口、内部节点、适用功能 |
| `subflow_instance` | 页面中实际使用的模块实例，包含端口接线和上下游 |
| `subflow_port` | 子流程输入/输出接口，支持端口级语义解释 |

子流程知识记录应至少包含：

```json
{
  "subflow_id": "string",
  "name": "末端组空新风/回风阀CO2控制",
  "status_in_template": "defined_only | instantiated",
  "instance_count": 1,
  "input_ports": [{"index": 0, "name": "string", "role": "sensor | command | setpoint"}],
  "output_ports": [{"index": 0, "name": "string", "role": "command | status"}],
  "instances": [{"node_id": "string", "tab_id": "string", "input_bindings": []}]
}
```

### 19.4 页面角色要抽象成工程骨架

AHU 三份模板体现出稳定骨架：

```text
IO/通讯 -> 控制 -> 定时 -> 直膨机状态
```

复杂版本会拆出：

```text
排风机、直膨机故障、直膨除湿模板
```

机房群控两份模板体现出两类骨架：

- 水系统群控示例：硬接&通讯信号、主机及蝶阀、冷却塔及蝶阀、冷冻&冷却泵、加减载&轮询、变频、动作先后判定。
- 风冷热泵标准工程：使用配置、硬接/调用信号、通讯信号、备用点位、风冷热泵控制、蝶阀控制、水泵控制、联动控制、旁通阀控制。

因此 `tab_label` 不能只做文本检索，应归一化为 `tab_role`。

建议 `tab_role`：

| `tab_role` | 示例页签 |
| --- | --- |
| `io_communication` | IO/通讯、硬接/调用信号、通讯信号 |
| `main_control` | 控制、风冷热泵控制 |
| `schedule_enable` | 定时 |
| `dx_status_mapping` | 直膨机状态 |
| `fault_mapping` | 直膨机故障 |
| `exhaust_fan_control` | 排风机 |
| `configuration` | 使用配置 |
| `spare_points` | 备用点位 |
| `equipment_standard_control` | 主机及蝶阀、冷却塔及蝶阀、冷冻&冷却泵、水泵控制、蝶阀控制 |
| `system_sequence` | 设备动作先后判定、联动控制 |
| `staging_rotation` | 设备加减载&轮询 |
| `variable_frequency` | 水泵&冷却塔变频 |
| `bypass_valve_control` | 旁通阀控制 |

咨询回答应能说清“这个问题主要落在哪些页面角色”，而不仅列出页面名。

### 19.5 模板类型要区分“示例逻辑模板”和“工程标准模板”

机房群控两份模板差异很大：群控示例程序没有真实 `hwInput/hwOutput/modbusOutput`，更像软件点逻辑示例；风冷热泵标准程序包含硬件、Modbus、BACnet 可见点、配置和备用点，更接近可交付工程模板。

因此模板索引应新增：

```json
{
  "template_archetype": "logic_example | engineering_standard | project_instance",
  "io_binding_level": "software_only | hard_io | communication_bound | mixed",
  "configurability": {
    "has_configuration_tab": true,
    "device_count_configurable": true,
    "max_device_count": 6
  }
}
```

检索和咨询边界：

- 逻辑示例模板适合回答控制顺序、动作关系和模块结构。
- 工程标准模板适合回答点位、通讯、硬件绑定和交付结构。
- 项目实例适合回答真实项目裁剪方式和差异。
- 不应把软件点示例模板误判为已具备现场 I/O 绑定能力。

### 19.6 配置页是系统拓扑知识，不是普通参数页

风冷热泵标准程序的 `使用配置` 页定义热泵总数量、水泵总数量、单机/从主、泵连接形式、季节模式等。这类页面决定系统拓扑和算法路径，应单独抽取为 `configuration_model`。

建议新增索引：

```text
indexes/advisory/configuration_model_index.jsonl
```

记录内容：

```json
{
  "template_id": "string",
  "project_type": "plant_room",
  "system_type": "air_source_heat_pump",
  "config_points": [
    {"name": "热泵总数量", "role": "device_count", "scope": "heat_pump"},
    {"name": "水泵总数量", "role": "device_count", "scope": "pump"},
    {"name": "泵连形式", "role": "topology", "enum": ["并联泵", "一对一"]},
    {"name": "季节模式设定", "role": "mode", "enum": ["制冷", "制热"]}
  ],
  "affects": ["设备轮询启停", "设备需求数", "热泵加减载", "水泵频率温压双控"]
}
```

当用户问“2 台改 4 台”“并联泵改一对一”“冬夏季模式怎么切”时，应优先检索配置模型，而不是直接进入普通补丁规划。

### 19.7 多设备位组合是群控知识重点

机房群控程序大量使用 `bitGroup`、`bitFetch`、`bitOperation` 表达多设备可用、运行、故障和命令状态。生产级咨询必须能解释：

- 某个位组合代表哪些设备。
- 第几位对应第几台设备。
- 组合位如何参与轮询、加减载和可用性判定。
- 修改设备数量时哪些位组合、子流程实例、点位和通讯映射需要同步。

建议新增链路类型：

```text
device_array_status_chain
device_rotation_chain
bitmask_mapping_chain
```

并新增字段：

```json
{
  "device_array": {
    "equipment_type": "pump | heat_pump | chiller | cooling_tower | valve",
    "max_count": 6,
    "active_count_source": "configuration | fixed_template | unknown",
    "bit_mapping": [
      {"bit": 0, "device_no": 1, "point": "1号热泵运行"}
    ]
  }
}
```

### 19.8 算法节点应按物理意义分类

AHU 和风冷热泵程序中出现 `enthalpy`、`wetBulbT`、`dewpointT`、`moisture` 等物理计算节点。它们不是普通数学节点，应进入领域知识检索。

建议新增 `algorithm_role`：

| 节点 | 角色 |
| --- | --- |
| `enthalpy` | 焓值计算 |
| `wetBulbT` | 湿球温度 |
| `dewpointT` | 露点温度 |
| `moisture` | 含湿量 |
| `pid` | 闭环调节 |
| `limit` | 输出限幅 |
| `runtime` | 运行时间累计 |
| `sort` | 轮值排序 |
| `statistics` | 运行数量统计 |

当用户问“焓值控制为什么影响新风”“热泵初始开启台数为什么看湿球温度”“除湿控制应该怎么接”时，应检索这些算法角色及其上下游。

### 19.9 画布布局是维护知识的一部分

结构对比明确指出 JSON 同时保存逻辑和画布布局。生产级咨询不一定需要生成布局，但需要利用布局理解工程师组织逻辑：

- `x/y` 可以辅助判断同一区域、同一注释块、同一设备实例。
- `comment` 节点可以作为功能分区和设备分组证据。
- 同页近邻不等于逻辑连线，但能辅助功能块边界识别。

建议功能块抽取加入布局聚类特征：

```json
{
  "layout_group": {
    "tab_id": "string",
    "bounding_box": {"min_x": 0, "min_y": 0, "max_x": 0, "max_y": 0},
    "nearby_comments": ["string"],
    "confidence": "low|medium|high"
  }
}
```

### 19.10 评测集必须覆盖结构对比揭示的问题

新增 advisory eval 必须覆盖以下问题：

- AHU：当前工程是否真正实例化 CO2 风阀控制，还是只保留子流程定义。
- AHU：直膨机故障点在 IO/通讯页还是独立直膨机故障页。
- AHU：排风机逻辑在控制页还是独立排风机页。
- AHU：`quote` 引用的原始 `swInput` 是哪个，最终影响哪些输出。
- 机房群控：模板是软件点示例还是工程标准模板。
- 机房群控：设备数量上限来自配置页还是固定实例数量。
- 机房群控：某个 `bitGroup` 的位含义和设备编号映射。
- 风冷热泵：`使用配置` 修改会影响哪些系统级模块。
- 风冷热泵：水泵频率温压双控涉及哪些输入、PID 参数和限幅。
- 通用：`wires` 必须按输入端上游来源理解，不能按标准 Node-RED 输出连线误读。

## 20. 推荐优先级

结合结构对比文档，优先级应从原来的“先知识卡、再抽控制链”调整为更偏项目代码事实建模：

1. 先实现 `wires` 输入端语义、`swInput/quote` 点位身份图和 `subflow_definition/subflow_instance` 分离。
2. 再实现 `tab_role`、`template_archetype`、`configuration_model` 和设备数组位映射。
3. 然后抽取控制链、保护链、通讯链、参数统计和历史模式。
4. 同步拆分领域知识卡，并把知识卡挂到 `tab_role/function_type/equipment/risk_tags`。
5. 最后接入 advisory 混合检索和回答契约。

这样做的原因是：如果底层工程事实抽错，后续领域知识再完善也会引用错误证据。生产级咨询首先要保证“看懂当前工程和历史模板”，再谈“给出设计建议”。

## 21. 最终目标形态

生产级咨询分支应达到：

```text
用户问工程设计问题
  -> 系统识别问题类型和工程对象
  -> 从当前工程、历史模板、领域知识、参数统计和风险规则检索证据
  -> 输出带证据、前提、风险、缺失信息、影响范围和验收建议的工程决策卡
  -> 用户可确认候选需求或采纳建议
  -> 采纳后仍进入补丁规划、dry-run、风险确认、校验和版本管理
```

这才是“生产级咨询分支”的边界：它不替代工程师，也不绕过工程安全流程；它把工程师需要查找、比对、审查和归纳的知识变成可追溯、可复核、可评测的决策支持系统。

# Deadline 演示脚本

更新时间：2026-05-01

用途：给项目演示、业务验收和新同事上手时使用。本文是固定演示路径，不是能力边界扩展清单；演示时优先照脚本输入，避免现场临时需求落入未覆盖样例。

## 1. 演示口径

当前版本交付的是面向 AHU 和机房群控标准模板的智能设计工作台：

- 通过多轮澄清和覆盖式记忆理解需求。
- 选择最合适的模板，并生成可审阅设计摘要。
- 用受控结构化补丁改造工程 JSON，不让 LLM 直接重写完整 JSON。
- 用局部图高亮展示本次变更影响范围。
- 导出前执行结构安全和需求覆盖双重校验。

明确边界：

- 不承诺从零生成任意复杂程序。
- 不自动应用中高风险补丁。
- 不自动接入 `copy_block` 外部边界线。
- 点表、IO/通讯、保护删除和设备数量变化必须人工确认。

## 3. 演示一：AHU 新建和低风险修改

目标：证明“需求理解 -> 模板选择 -> 设计摘要 -> 创建版本 -> 低风险改造 -> 局部图定位 -> 校验导出”闭环。

步骤：

1. 顶部选择 `AHU 程序`。
2. 点击 `新建`。
3. 输入需求：

```text
我要做 AHU 程序，需要直膨机、排风机、CO2 控制、新风阀和 Modbus 通讯。
```

4. 观察左侧结构化需求：
   - 项目类型：AHU。
   - 设备：直膨机、排风机、新风阀。
   - 控制功能：CO2 控制。
   - 通讯/IO：Modbus。
5. 观察模板候选和设计摘要：
   - 推荐 6 页结构 AHU 模板。
   - 展示已满足项、需改造项、风险项和导出门禁提示。
6. 点击第一个模板的确认按钮。
7. 等待顶部出现 `版本：v_...`。
8. 输入低风险修改：

```text
把节点 1154c92 改名为 演示-AHU比较节点
```

9. 观察结果：
   - 系统自动应用低风险改名。
   - 版本号变化。
   - 右侧局部图显示 `自动定位 1154c92`。
   - diff 显示修改 1 个节点。
10. 点击 `校验`。
11. 校验通过后点击 `导出`。

验收点：

- 不需要手写 JSON。
- 设计摘要可读。
- 低风险补丁自动落为子版本。
- 局部图定位到 affected 节点。
- 导出前经过校验。

## 4. 演示二：机房群控中风险确认、版本 diff 和回滚

目标：证明中风险修改不会直接落盘，必须 dry-run 和人工确认；确认后可查看版本 diff 并回滚。

步骤：

1. 顶部选择 `机房群控程序`。
2. 点击 `新建`。
3. 输入需求：

```text
我要做一个风冷热泵机房群控程序，包含水泵、旁通阀和 Modbus 通讯。
```

4. 确认推荐模板。
5. 记录当前版本号。
6. 输入中风险修改：

```text
断开节点 2853d21 的输入 0
```

7. 观察结果：
   - 出现 dry-run 通过。
   - 出现“确认后才会创建新版本；取消不会改变当前版本”。
   - 当前版本号不变。
8. 点击 `确认应用`，并在弹窗里再次确认。
9. 观察版本号变化。
10. 打开 `版本 / Trace / 反馈`。
11. 在版本历史里查看父子版本 diff。
12. 对新版本执行回滚，确认回到原版本。

验收点：

- 中风险操作不会自动落盘。
- dry-run 通过后才允许确认。
- 确认后创建子版本。
- 版本 diff 可查。
- 回滚只切换当前指针，不删除历史版本。

## 5. 演示三：需求覆盖门禁

目标：证明“JSON 合法”不等于“满足用户明确需求”；覆盖缺失时会阻塞导出。

步骤：

1. 顶部选择 `AHU 程序`。
2. 点击 `新建`。
3. 输入需求：

```text
AHU 需要过滤网报警和防冻保护，通讯走 Modbus。
```

4. 确认模板。
5. 点击 `校验` 或直接尝试导出。
6. 观察需求覆盖报告。

期望：

- 结构校验可以通过。
- 需求覆盖报告会提示过滤网报警或防冻保护缺少可证明线索。
- 导出被阻塞。

演示口径：

```text
这里证明系统不会只因为 JSON 结构合法就导出。用户明确提出的业务需求如果找不到证据，会进入需求覆盖门禁，防止把潜在缺失留到下一阶段。
```

## 6. 演示四：高风险 IO 点位确认

目标：证明 IO/通讯点位修改必须人工确认，并展示点表字段复核提示。

可用后端验收命令：

```powershell
conda activate midea
pytest -q tests/test_business_acceptance.py::test_business_acceptance_high_risk_io_patch_requires_and_resumes_confirmation
```

工作台演示输入可采用：

```text
把节点 22a27d1 的物理输入通道改为扩展模块 1、通道 31。
```

期望：

- 风险等级为 high。
- dry-run 不保存版本。
- 确认摘要提示点表字段和值、通道/地址/对象号冲突和现场接线/通讯表复核。
- 确认后才创建新版本。

## 7. Trace 和反馈演示

目标：证明系统过程可追踪。

步骤：

1. 完成任意一次会话。
2. 打开 `版本 / Trace / 反馈`。
3. 查看：
   - `事件流`：工作流步骤、版本创建、校验完成。
   - `Trace`：trace id、用户输入、事件数量、失败事件、LLM 调用摘要和关键产物摘要。
   - `指标`：事件、LLM 成本和趋势。
   - `反馈`：提交当前演示反馈。

推荐反馈内容：

```text
演示验收：需求理解、模板选择、设计摘要、局部改造、校验和导出链路通过。
```

## 9. 常见现场问题

导出按钮不可用：

- 先看结构校验是否存在 error。
- 再看需求覆盖报告是否存在 blocked。
- 如果用户需求明确要求防冻、过滤网报警、旁通压差等，而当前工程缺少证据，阻塞是预期行为。

LLM 不可用：

- 低风险规则 planner 和手动结构化补丁仍可用。
- 复杂结构改造会返回需要补充页面、节点 id、端口和点位字段的追问。
- 真实 LLM 演示前必须配置 `.env` 中的 `DEEPSEEK_API_KEY`。

局部图没有显示全量工程：

- 这是预期行为。前端只加载预算受控摘要，默认聚焦 affected 节点和相关页签，避免拉取 900 到 2000 个节点的完整 JSON。

现场不要演示的内容：

- 从零生成任意复杂工程 JSON。
- 自动删除保护链路。
- 自动复制功能块并接全部外部线。
- 无点表依据批量改 IO/通讯地址。
